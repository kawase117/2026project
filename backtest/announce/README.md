# ホール予告の事前登録と答え合わせ

`backtest/announce.py` のデータ置き場。運用手順と、閾値をどう決めたかの記録。

## なぜこれをやるか

ホールは対象日より前に具体的な予告を出している（楽園 `kawasakislot` の「全⑤⑥×2機種あり」
「Lカバネリが1/2⑤⑥」、蒲田1 のリアルアイ予想「全台系あり・水曜→ニブイチ末尾×2本以上」など）。
これは我々が過去データから作るスコアより情報量が多い可能性があるのに、
2026-08-06 まで蓄積がゼロだった。毎回セッションで読んで捨てていた。

予告と統計は競合しない。役割が違う。

- **予告** が「何が起きるか」を教える（全台系が2機種ある）
- **統計** が「どれか」を絞る（候補60機種のうちどの2機種か）

単独で台を当てるより桁違いに易しい問題設定になる。

## 閾値は分位点ではなく絶対値で固定する（2026-08-06 の設計変更）

最初は「過去90日の機種×日スコア分布の95パーセンタイル」を全台系の閾値にした。
これは **誤り** である。`baserate` を全ホールで回すと、閾値超え機種数/日が
例外なく「候補機種数 × 0.05」に一致した。

| ホール | 候補機種/日 | 95%ile閾値 | 閾値超え/日(平均) | 候補×0.05 |
|---|---|---|---|---|
| 楽園蒲田店 | 61.5 | +1,824.3 | 3.08 | 3.08 |
| マルハンメガシティ2000-蒲田7 | 60.4 | +2,114.5 | 3.02 | 3.02 |
| マルハンメガシティ2000-蒲田1 | 46.7 | +1,898.8 | 2.34 | 2.34 |
| ヒロキ東口店 | 43.4 | +1,904.4 | 2.17 | 2.17 |
| みとや大森町店 | 32.0 | +1,710.8 | 1.61 | 1.60 |
| ザ-シティ-ベルシティ雑色店 | 14.7 | +1,996.3 | 0.74 | 0.74 |

（窓 2026-05-08〜2026-08-06、`min_machines=3`、`--pct 0.95`）

分位点で閾値を切る限り、これは恒等式であって観測ではない。
この閾値のもとでは `zentaikei_count`（「全台系がN機種ある」）は
**構成上ゼロ情報** になり、当たっても何も学べない。

したがって閾値は **ホール共通の絶対値 +1,800** に固定する。

根拠は物理側から出す。全台系（設定6・機械割 109%）のジャグなら
差枚率 ≒ 0.09 × 3 = 0.27枚/G。5,000G 回れば +1,350枚。
全台系の島は人が集まるので G比は 1.3〜1.4。
よって `G比 × 平均差枚 ≒ 1.35 × 1,350 ≒ +1,800`。

分位点推定（1,711〜2,115、中央 約1,900）が独立にこの水準へ収束していることは
補強材料になるが、**採用根拠は物理側**である。分位点は妥当性チェックに一度使うだけ。

絶対値に固定した効果:

- `zentaikei_count` が「ホールが実際に何機種投入したか」の観測量になる
- ホール間比較ができる（雑色の投入量が少ないことが数値に出る）
- `model_named` のベースレートが構成ではなく実測で決まる

## 閾値 +1,800 の実データ校正（2026-08-06）

**当たった例**: 楽園蒲田 2026-08-04 のシャーマンキング（n=5, 平均差枚 +2,581, gratio 0.71,
score **+1,824**）は閾値を超えた。この機種は結果報告アカウント `slokotae7`（Zeno）が
独立に「【全台系】Lシャーマンキング +3/5台 平均+2,498枚」と報告した機種と一致する。
**第三者が全台系と認識した機種を、本指標と閾値が独立に検出できている。**

**既知のバイアス — 少台数機種に有利**:

| みとや 2026-08-04 | 台数 | gratio | 平均差枚 | score |
|---|---|---|---|---|
| やじきた道中記参る！ | 4 | 0.99 | +2,346 | +2,323 |
| ソードアート・オンラインII | 4 | 1.95 | +1,109 | +2,158 |
| とある魔術の禁書目録2 | 5 | 1.22 | +1,677 | +2,048 |
| 甲鉄城のカバネリ 海門(うなと)決戦 | 17 | 1.06 | +1,264 | +1,339（rank 5、閾値未満） |

`G比 × 平均差枚` は台数を見ない。4台の機種は2台が跳ねれば平均が上がるが、
17台の機種は全台が働かないと上がらない。**本来いちばん検出したい大規模な全台系島ほど不利**
という構造になっている。

ただしこの日のカバネリは勝率 10/17、上位2台（640番台 +9,136・633番台 +7,528）で
総和の 78% を占めており、真の全台系ではなかった可能性が高い。
その意味では閾値未満という判定は正しいかもしれない。

**この指標は変更しない。** `hist_model_gratio_mean_diff` は 2026-08-01 に正解ラベル6件で
検証して選ばれたものであり、上の観察だけを根拠に差し替えると検証済みの選択を
未検証の思いつきで上書きすることになる。台数一貫性（勝率・下側分位点）を加える案は、
**別の指標として新規に登録し、同じ土俵でフォワードして比べる**こと。

## 新台は除外せず層別する（2026-08-06 計測）

上の校正表でカバネリを抜いた「やじきた道中記参る！」「とある魔術の禁書目録2」は
どちらも **2026-08-03 初出＝08-04 時点で導入2日目の新台** だった。
新台は設定不問で高回転するので G比が構造的に膨らむ
（instinct: `shindai-exclude-from-games-analysis`）。

6ホール・2026-05-08 以降・30,039 機種日での計測:

| 導入からの日数 | 機種日数 | 平均score | G比(中央値) | 平均差枚 | 閾値+1800超え率 |
|---|---|---|---|---|---|
| 0-6日 | 657 | -668 | 1.42 | -315 | **10.5%** |
| 7-13日 | 628 | -390 | 1.15 | -249 | 9.7% |
| 14-29日 | 1,450 | -281 | 0.98 | -212 | 8.0% |
| 30-59日 | 1,917 | -272 | 0.91 | -158 | 6.6% |
| 60日+ | 25,387 | +100 | 0.84 | +40 | **4.8%** |

**向きが重要である。新台は平均的には負けている**（平均差枚 -315枚）。
「新台は販促で高設定が入る」という通説は、この期間・このホール群では成立しない。
回転数だけが多く差枚はマイナス、つまり客が突っ込んでいるだけである。

それでも閾値超え率が 2.2 倍（10.5% vs 4.8%）なのは、G比が 1.7 倍あるため
平均差枚が少しプラスへ振れるだけでスコアが跳ねるから。**期待値ではなく分散が大きい。**
実際、閾値超え機種の 15.5% が導入30日未満（母集団比率は 9.1%）で 1.7 倍の過剰代表。

分散の大きさは実例で確認できる。同じ「やじきた道中記参る！」（導入2日目）が
2026-08-04 に **みとやでは rank 1/36（score +2,323）、楽園では rank 56/56
（score -4,201、G比 2.19・平均差枚 -1,920）**。同一機種・同一日で最上位と最下位。

### 除外してはならない

ホールが新台に全台系を入れることは実在する
（`kawasakislot`「前回新設島に導入された鉄拳6は導入当日、翌日と2日間連続で全56に」）。
候補から外すと本物を取り逃がす。

正しい対処は **層別** である。`score` サブコマンドは `model_named` の判定に
`age_days` / `age_bucket`（`new` = 導入30日未満 / `established`）/ `base_rate` を併記する。
`zentaikei_count` には `n_new_machines_over`（閾値超えのうち新台の数）が付く。

**予告が新台を名指ししたら 10.5%、既存台なら 4.8% と比べること。**
単一のベースレートで的中率を出すと、新台を名指しするだけで
「予告は有効」に見えてしまう。ホールの予告は新台を名指ししがちなので
（楽園「最新台の■とある魔術の禁書目録2（8台）…も朝から打てます」）、
この混同は実際に起きる。

なお `BASE_RATE_OVER_THRESHOLD` の値は 2026-08-06 時点・閾値+1,800 での実測である。
閾値を変えたら測り直すこと。

## 台数バイアスへの対抗指標 winrate_lb95_gratio（2026-08-06 追加・未検証）

`gratio_mean_diff` は台数を見ないため少台数機種に有利という構造バイアスがある
（上の校正表参照）。対抗指標として `winrate_lb95_gratio` を追加した。

```
score = 勝率のWilson下限95%（対プール平均） × G比 × max(平均差枚, 0)
```

台数が少ないほど Wilson 下限が強く縮むため、「少数台が偶然跳ねただけ」を
構造的に罰する。みとや 2026-08-04 で比較すると:

| 機種 | 台数 | gratio_mean_diff | rank | winrate_lb95_gratio | rank |
|---|---|---|---|---|---|
| やじきた道中記参る！（新台） | 4 | +2,323.2 | 1 | +698.4 | 1 |
| とある魔術の禁書目録2（新台） | 5 | +2,048.2 | 3 | （圏外） | — |
| マイジャグラーV | 34 | — | 圏外 | +449.3 | **4** |
| 甲鉄城のカバネリ 海門(うなと)決戦 | 17 | +1,338.7 | 5 | +414.5 | **5** |

マイジャグラーV（34台）が新指標では上位に入り、とある禁書目録2（新台・5台）は
上位から落ちた。台数を重く見る方向には動いているが、**それでも4台のやじきた
道中記参る！が1位のまま**なので、バイアスが解消したとは言えない。

**既存指標を置き換えない。** `zentaikei.metric` に `"gratio_mean_diff"` か
`"winrate_lb95_gratio"` を指定でき、`baserate --metric winrate_lb95_gratio`
で個別に閾値を出せる。閾値のスケールが全く違う（gratio_mean_diffは千の位、
winrate_lb95_gratioは百の位）ので、既存の絶対閾値 +1,800 を流用しないこと。
`BASE_RATE_OVER_THRESHOLD` の新台バイアス実測値（10.5% / 4.8%）は
`gratio_mean_diff` 専用で、`winrate_lb95_gratio` 側はまだ計測していない。

両指標を同じ予告に対して走らせ、`model_named` の的中率を指標別に比較できる
だけのサンプル（目安20件超）が溜まってから、どちらを主指標にするか判断する。
それまでは `gratio_mean_diff` を主、`winrate_lb95_gratio` を参考として扱う。

## 何を測っているのか

**測るべき唯一の量は `model_named` の的中率である。**

`zentaikei_count` は「予告が何を言ったか」の記録として残すが、検定ではない。
候補が約60機種あるホールで、閾値超えは1日あたり2〜3機種。
機種を名指しして当てられるなら、それはランダム（約5%）を大きく超えるはずである。

判定に必要なのは 20 件程度の登録。それまでは的中率を報告しない。

## 運用手順

1. **閾値の確認**（初回とホール追加時のみ。毎回はやらない）

   ```
   venv\Scripts\python.exe -m backtest.announce baserate 楽園蒲田店 --before <target_date> --days 90
   ```

2. **予告 JSON を書く。** `threshold: 1800.0` を固定で入れる。
   `source.kind` は `"予告"` のみ。結果報告アカウント（`slokotae7`、`sloneko222`）や
   店長アカウントの投稿を予告として登録しない。
   `posted_at` は対象日 0 時より前でなければ `register` が拒否する。

3. **登録（凍結）。** 対象日のデータが DB に入る前に実行すること。

   ```
   venv\Scripts\python.exe -m backtest.announce register backtest/announce/<announce_id>.json
   ```

   `LEDGER.jsonl` にダイジェストが追記される。以後 JSON を書き換えると採点時に検出される。

4. **答え合わせ。** 対象日のデータ取り込み後。

   ```
   venv\Scripts\python.exe -m backtest.announce score backtest/announce/<announce_id>.json
   ```

## 判定の読み方

`hit` は **True / False / None の3値**。`None` は「判定不能」であって外れではない
（機種の撤去・設置台数不足・表記ゆれ・比較対象が空）。
的中率を出すときに `None` を `False` に混ぜないこと。

`model_named` が `None` になる典型は **機種名の表記ゆれ** である。
DB の `machine_name` と投稿の表記は一致しないことが多い
（投稿「Lカバネリ」 vs DB「甲鉄城のカバネリ 海門(うなと)決戦」）。
登録時に DB 側の正式名称へ変換しておくこと。変換を怠ると
「当たらなかった」ではなく「測れなかった」が積み上がる。

## やってはいけないこと

- **採点後に threshold を変えること。** 閾値は登録時に凍結され、`LEDGER.jsonl` に記録される。
- **結果報告を予告として登録すること。** 的中率が定義上 100% になる。
  `kawasakislot` と `999999Q9Q` は予告も結果報告も投稿する同一アカウントなので、
  アカウント単位ではなく **投稿単位** で `posted_at` を確認する。
- **hit104率を判定指標にすること。** Var(機械割) ∝ 1/games なので回転数の多寡を
  設定差として計上してしまう（instinct: `answer-check-metric-hit104-over-mean-diff`）。
- **カテゴリ平均で `category_share` を判定すること。** ホールがカテゴリ内で特定機種に
  集中投入した場合に見逃す（instinct: `category-aggregate-hides-reallocation`）。
  本モジュールの `category_share` は「閾値超え機種のうち何割がそのカテゴリか」で定義してある。
