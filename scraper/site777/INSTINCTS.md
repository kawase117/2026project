# Site Seven（楽園蒲田）収集・分析 Instinct

`output/` はGit管理外のため、この文書を `scraper/site777/INSTINCTS.md` に置いて追跡する。

## 検証済み: 通常遷移と低頻度アクセスを基本にする

- 深いURLへの直接HTTP取得では、HTTP 200でも `PNW500029` / `PNW500034` のエラー画面になることがある。
- 永続ブラウザプロファイルでCookieを保持し、機種一覧 → 機種ページ → 各データページという通常のリンク遷移を行った。
- 5秒間隔、単一ブラウザ、必要時のみ1回の再読込という条件で、グラフ取得920アクセスは制限0件・取得失敗0件だった。
- 過剰な並列アクセスや即時の連続再読込は行わない。混雑時は待機してから再試行する。
- 2026/08/12の再検証では、機種メニューから抽出した深いURLへ直接移動すると、エウレカとマイジャグラーで `PNW500034` が継続した。同じ永続プロファイルで、一覧→機種→データをCtrlクリックによる通常遷移へ戻すと、両機種とも再読込なしで成功した。
- 自動化では深いURLへの直接移動を正常系にしない。`PNW500034` を単なるサイト全面障害と判定する前に、親ページからのクリック遷移が守られているか確認する。
- 回復順序は、同一タブの再読込を即時1回、その後1分、5分とする。回復しなければ停止し、短時間に新しいブラウザセッションを連続起動しない。

## 検証済み: 表データとグラフデータは取得コストが大きく異なる

- 表データの全台取得は378アクセス・約39分だった。
- 出玉推移グラフは各台の個別ページが必要で、587台の全取得は920アクセス・約94分だった。
- 差の主因はOCRではなく、グラフの台別ページ取得数と5秒待機である。OCRは446画像を約24秒で処理できた。
- グラフ取得は「取得バッチ → 未処理画像だけOCR → 差枚推定 → 保存」とし、ネットワークアクセスとローカル処理をパイプライン化する。

## 検証済み: 最新差枚はグラフ画像から推定できる

- グラフの縦軸ラベルをOCRし、紫色の推移線の終点Y座標を縦軸へ線形換算する。
- 推定値は10枚単位に丸める。典型的な縦方向の解像度は約31枚/pxであり、厳密な実差枚ではなくグラフ由来の推定値として扱う。
- 少ゲーム台では線が短く低信頼になる。今回の低信頼2台はいずれも46G・53Gだった。
- 0G台はグラフ線がなくても、差枚0・勝ち台ではないとして扱える。

## ランキングの完全性と時刻の扱い（2026-08-16 訂正）

粒度によって「生成しない」と「除外して生成する」を使い分ける。以前の版はこの2つを混同していた。

- **収集ラン全体が未完了なら生成しない。** 一覧が `complete=false`、またはしきい値以上の台で差枚が1台でも欠ける場合は、`site777_analyze.py` が `SystemExit` で停止する。
- **個別機種が未完了なら、その機種だけ除外して生成する。** `complete=false` の機種は集計から落とす。
- **一覧とグラフの取得時刻が違っても生成する。** 「別時刻データ」と明記し、大当り・最高出玉・グラフの3時刻を行内に併記する。時刻一致を生成条件にはしない（以前の版の「時刻が一致しない場合は生成しない」は誤り）。
- 勝率は「推定最新差枚が0枚より大きい台数 ÷ 差枚取得成功台数」とする。
- 機種別・一台機種・末尾別の各ランキング表には、平均差枚・平均G・勝率を共通表示する。
- 一台機種と末尾別は、通常の機種別ランキングとは別レポートにする。

## 運用仮説: 更新窓を先に確認してから全量取得する

- 当日の観測では更新時刻に `:25` / `:55` が見られた。30分更新の可能性があるが、複数日の観測で確定するまでは仮説として扱う。
- 次回はまず少数の監視台で更新時刻だけを確認し、前回と時刻が同じなら全量取得を見送る。
- 更新が確認された場合にだけ表データを全量取得し、グラフは差枚が必要な回だけ取得する。これがサイト負荷と実行時間の両方を最も減らす。

## 2026-08-16: レポート指標の是正

- **率指標には母数の下限を課す。** 勝率ランキングを母数なしで並べると、有効差枚1〜2台の機種が100%で上位を独占していた。有効差枚 `MIN_RANKED_DIFF_MACHINES`(=3) 台以上に限定する。一台機種は定義上この条件を満たさないため、勝率ランキングは空になるのが正しい。
- **BB/RB/合成確率のランキングはノーマル機だけで作る。** 全機種を混ぜると、擬似ボーナスのAT機（ワールドダイスター、L化物語など）が上位を占める。AT機のBB/RB回数は仕様値で設定と無関係。対象区分は `jug` / `hana` / `oki` / `bt`。是正後の上位は新ハナビ・ゴーゴージャグラー3・ネオアイムジャグラーEX・沖ドキ！BLACK・キングハナハナ-30。
- **一覧とグラフの時刻差は符号を落とさない。** 並行パイプラインではグラフのほうが新しくなるため、`max(0, ...)` で下側をクリップすると片方向のズレが常に0分に見える。符号付き `graph_time_skew_minutes` と絶対値 `graph_age_minutes` を分けて持つ。実測の符号付きズレは `-30, 0, 60, 120, 180, 210, 270` 分。
- **「角番」と呼んでよいのは `rank_from_aisle`（通路角番）と `rank_from_min`/`rank_from_max`（台番号順）だけ。** 座標から復元した列の端は別概念なので「列端位置」と呼ぶ。楽園蒲田店の `machine_layout` は `rank_from_aisle` が全587台NULLで、通路角番は算出できない。列端位置の結果を既存の角番分析と直接比較しない。
- **設定期待と出玉実績を混ぜない。** 判定は累計G・累計BB・累計RBだけで行う。固定設定を仮定する限り、直近区間の不振は累計成績と独立した根拠にならないので、マイナス材料として二重計上しない。ノーマル機でRB確率が機種平均より良い台を「高設定期待(RB)」、BBだけ機種平均超えの台を「出玉候補(BB偏重)」、AT機・マスター未対応機は差枚がいくら良くても「出玉候補(設定判定外)」に留める。
- **機種マスター未マッチは黙って落とさない。** 実測で587台中187台・55機種が未マッチだった。`site777_analyze.py` の標準出力に機種名を全件出し、`config/machine_aliases.json` を埋められるようにする。
- **機種名の照合は「厳密キー優先 → 接頭辞除去キーでフォールバック」。** サイトセブンは `LB` / `スマスロ` / `パチスロ` / `SLOT` / `A-SLOT+` / `回胴式遊技機` を接頭辞として付けるが、機種マスターは付けないことがある。旧実装は先頭の `L` だけを剥がし、しかも `LB` 始まりは明示的に除外していたため、`LBサンダーV`・`LB SHAKE BONUS TRIGGER`・`パチスロ戦国恋姫`・`パチスロ ピンクパンサーSP` などのAタイプがまとめて未マッチだった。
  接頭辞除去キー**だけ**で索引を作ってはいけない。`スマスロ ドルアーガの塔` と `SLOTドルアーガの塔` が同じキーに潰れ、実測で現在マッチ済みの5機種が衝突で失われる。厳密キーを先に引き、外れた場合だけフォールバックすると退行ゼロで、マッチが587台中400→550台に増える（未マッチ機種55→9、フォールバック由来136台）。
- **RBが全台0回の機種は、区分がノーマル機でも確率ランキングから外す。** RB契機のない機種なので、機種マスターの `bt_flag` が誤っていてもこの条件で落ちる。実測では `交響詩篇エウレカセブン HI-EVOLUTION ZERO TYPE-ART`（25台、3215-3239）が該当。同じ `bt_flag=1` には他にもAT機が混ざっている（ダンジョンに出会いを求めるのは間違っているだろうか2、蛇喰夢子という女、ヱヴァンゲリヲン～約束の扉～ など）ので、bt_flag を無条件に信用しない。
- **機種横断のRB確率ランキングは設定の情報を持たない。** マイジャグラーVの設定1は1/409.6、設定6は1/229.1、ゴーゴージャグラー3は1/378.8〜1/262.1と、設定差より機種差のほうが大きい。機種をまたいでRB確率を並べても機種仕様を並べているだけになる。BB/RB確率のランキングは同一機種内の比較にとどめ、設定を読むならスペック表と突き合わせる。
- **設定はピンポイントで当たらない。判定できるのは高低どちら寄りかだけ。** スペック表からの合成試行（2万試行/条件）で、8,000G回しても最尤設定が真の設定に一致するのは3〜4割（6択の偶然は16.7%）、±1以内で6〜8割。単一の推定設定を出すと6割以上外れる。
- **信用度に「最尤設定と2位の尤度差」を使ってはいけない。** 1位と2位は必ず隣り合う設定になるため、実データ78台では最大でも2.2倍にとどまり全台が「低」に潰れた。`max L(設定5,6) / max L(設定1〜4)` の高低尤度比を使うと 高5/中19/低54 に分かれて機能する。事前分布を仮定しないので「その台が高設定である確率」ではなく、台どうしの相対比較に使う。
- **高設定の判定は低設定の判定より回転を要する。** 設定4が5-6に近いため非対称になる。マイジャグラーV相当のスペックで、設定6ちょうどの観測は6,000Gで尤度比2.11倍（信用度低）、8,000Gで3.03倍（中）。一方、設定1ちょうどの観測は6,000Gで低側へ4.8倍（中）に達する。
- **ゴーゴージャグラー3は誤警報が多い。** 真が設定1でも最尤が設定5-6と出る割合が、3,000Gで22.7%、5,000Gでも17.2%。設定間のスペック差が小さいためで、回転数では解消しない。マイジャグV・アイムEX・ハッピーⅧは3,000Gで8〜13%。
- **アイムジャグラーEX系は設定5と6を原理的に分離できない。** RB確率がどちらも1/255.0、BB確率も1/259.0対1/255.0でほぼ同じ。8,000G回しても「設定6を6と当てる」率は34.8%で頭打ちになる。回転数の問題ではないので「5-6」と統合して扱う。
- **推移線の色は変わる。決め打ちしない。** 2026-08-17にサイトセブンが線色を青紫(103,99,245)系から橙(251,134,103)系へ変更し、紫・青・黄の3マスクすべてに外れて143台全部が `trace_unreadable` になった。橙は黄色マスクの `(green - blue) >= 50` に対し実測31で僅差で落ちていた。軸ラベルのOCRは正常だったので「白紙」ではない。`tracePixels=0` を見たらまず線色を疑い、画像の色分布を数えること。結果に `traceColorCounts` を出すようにしたので、次からは内訳で即座に判別できる。
- **検出ロジックを変えたら `inputSignature` のバージョンを上げる。** `site777_graph_analyze.py` は `v6:<lastWriteTimeUtc>:<length>` で解析結果をキャッシュする。バージョンを据え置くとコードを直しても既存画像に再適用されず、`processedThisRun=0` で何も変わらない。再スクレイピングは不要で、バージョンを上げて再解析すればよい。
- **「RBが全台0」を母数を見ずに構造的欠如と断定しない。** 実測（8/17 13:55）で、本当にRB契機がないエウレカTYPE-ARTは43,499G/RB0だったのに対し、誤検出された4機種（ピンクパンサーSP・キングパルサー・ハイパーラッシュ・沖ドキ!DUO）は93〜696Gで単に引いていないだけだった。累計3,000G以上を条件にする。
- **午後の速報では設定推定はほとんど効かない。** 8/17 13:55時点でスペック表対象117台のG中央値は824Gで、2,000G以上は9台のみ、しかも全台が信用度「低」だった。設定推定を使うなら夕方以降に取得する。
- **`.ps1` に日本語を一切書かない。コメントも文字列リテラルも。** BOMなしUTF-8のPS1をWindows PowerShell 5.1はANSIコードページ(cp932)として読む。`pwsh.exe`(PowerShell 7)なら正しく読むが、この環境に`pwsh`は入っておらず `run_site777_complete.cmd` は常に `powershell.exe` へフォールバックする。
  - 日本語**コメント**を1行足すと、数行先の `}` が `UnexpectedToken` になる。
  - 日本語**文字列リテラル**は構文エラーにならず、**黙って別の文字列に化ける**ぶん危険。実測（2026-08-17）で `--reference-db (Join-Path $projectRoot 'db\楽園蒲田店.db')` が `db\楽園蒲田庁Edb` に化け、収集26分＋グラフ364台が全部済んだ最後の解析段階で `FileNotFoundError` になった。`db/` に0バイトの `楽園転田店.db` が残っており、同じ事故は過去にも起きている。
  - 対策はパスをPS1に書かないこと。`reference.py` の `DEFAULT_REFERENCE_DB` がPython側で同じパスを解決するので `--reference-db` は渡さない。
  - 点検は `LC_ALL=C grep -an '[^ -~\t]' *.ps1` で非ASCII行を全滅させる。構文確認の
    `[System.Management.Automation.Language.Parser]::ParseFile($path,[ref]$null,[ref]$errs)` は
    **構文が通っても文字列の化けを検出できない**ので、非ASCIIチェックのほうが本質。
- **`machine_master` 側に表記ゆれの重複がある。** 正規化キー衝突として、先頭空白違い（`" サンダーマンボマンボ"` と `"サンダーマンボマンボ"`、`" ULTRAMAN"` と `"ULTRAMAN"`）と、感嘆符の全角/半角違い（`"押忍!番長"` と `"押忍！番長"`、`"喰え!ハーレムエース"` と `"喰えっ！ハーレムエース"`）が検出された。衝突したキーは自動対応を諦めるため、マスター側の整理が必要。
