# 遊技収支帳：次の開発方針と決定事項

作成日: 2026-10-21。目的は、一般公開を急ぐ前に「既存のぱち簿データを失わず、毎日の記録を迷わず付けられ、分析値の意味が分かる」状態にすること。これは実装順の提案であり、未実装機能を完成済みと表現しない。

## 推奨する順番

| 順 | 作業 | 完了の判断基準 |
|---|---|---|
| 1 | データ保護と編集の整合 | 新規・取込・台移動付き記録で作成・訂正・削除を検証する。削除前後それぞれの JSON/ZIP を空DBへ復元し、各時点の件数・金額・タグ・計算条件が一致する。削除前のバックアップ導線と復元手順を文書化する |
| 2 | 主な操作の実機相当検証 | API 26 と現行の新しい API のエミュレーターで、スロットの開始→終了、後入力、タグ、機種・ホール候補、編集・削除、ダークモード、日付選択、ファイル保存を操作する。小画面、文字拡大、左手操作、縦スクロール量を確認する |
| 3 | ぱち簿互換性の検証拡大 | 個人情報を除いた複数の実バックアップまたは再現用フィクスチャで、取込対象件数・タグ・文字・金額・未分類理由を照合する。衝突時の挙動と原本保存を検証する |
| 4 | 分析の信頼性向上 | 指標ごとに対象件数・除外件数・定義を示す。期間や種別を変えても仕事量と実収支が混ざらない。少数件・複数タグ・台移動・経費を含む比較の誤解を防ぐ。集計速度も計測する |
| 5 | 公開準備 | パッケージ名・公開用ビルド・署名・プライバシーポリシー・ストア説明・問い合わせ先・広告と課金の方針を確定し、提出時点の Google Play 要件を公式資料で再確認する |

**提案の理由:** 現在もっとも避けたい失敗は、収支の誤集計やバックアップ不能のまま多くの利用者に配ること。分析や広告は、データの正しさと日常入力が安定して初めて価値を持つ。新しい分析指標や自動機種マスターは、その後に優先度を付ける。

## 先に決めるべき仕様

| 論点 | 推奨案 | 判断が必要な理由 |
|---|---|---|
| 取込記録の編集 | 日常操作は新規記録と同じ入口に寄せ、原本の内訳不明な円換算額だけ明示する。内部形式は移行せず保持する | 金額の内訳を推測して統合すると元データを壊す |
| 履歴の削除 | 削除前に対象内容を確認し、少なくともバックアップから復元できる道を確保する。必要なら一定期間のゴミ箱を設ける | 現行は確認後に削除すると直接の取消しがない |
| 交換率の履歴 | その記録で使った交換率を保持し、編集時にも当時の値を初期表示する。ホールの現行設定更新だけで過去収支・仕事量を変えない | 実際に交換率と再プレイ上限は時期で変わる |
| パチンコの仕事量 | 4円パチンコの計算式と入力単位を固定して記録し、手入力との区別を残す。仕事量を「予測された利益」と呼ばない | ボーダー、回転率、持ち玉比率、交換率の入力誤差が大きく効く |
| 分析の比較 | 実収支、計算仕事量、回転数を別の列として提示する。上位順は対象件数と期間を併記し、事後探索から勝てると断定しない | 直近の好成績だけを選ぶと偶然の優位性を発見しやすい |
| 自動バックアップ・Dropbox | 最初の公開版では手動の完全ZIP/JSON保存・復元を確実にする。自動同期は競合解決と認証を設計してから判断する | 複数端末の同時編集は二重登録や上書き損失の原因になる |
| 無料・有料 | 初版は単一アプリ＋買い切り広告解除を候補とし、基礎記録・移行・バックアップは無料側にも残す | 別アプリにすると記録移行と購入復元が複雑になる。現時点で課金処理は未実装 |

## 公開前に残る具体的なリスク

1. **移行データ:** `.pcb` は公開仕様でない。取込対象外、種別不明、原本との衝突を利用者に説明できる画面とログが必要。
2. **編集の差:** 新規セッションと取込レコードの編集画面が異なり、過去の円換算額は現金・貯玉の内訳に自動分解できない。UIでは差を隠さず、誤認しやすい入力だけ整理する。
3. **バックアップ:** 現状はファイルを利用者が保存する方式。別端末・更新後の復元成功を確認してから日常利用を勧める。
4. **入力負荷:** 一台開始前と終了後の操作を実測する。スロットが大半という使い方に合わせ、4円パチンコの詳細欄は必要なときだけ見せる。
5. **公開設定:** Android の `applicationId` は試作名、`targetSdk` は35、`versionCode` は1。リリース用設定、署名、申請、広告・課金、ストアの審査は未着手。
6. **個人データ:** `.pcb` や出力ZIPには遊技履歴、ホール、メモ、タグが入る。GitHubへ置く前に個人のバックアップ、生成DB、APK、検証出力を除外する対象を決める。

## 作業単位の提案

- **次の一回:** 保存・復元、編集・削除、交換率の履歴に関する失敗ケースを検証し、再現した不具合だけ修正する。
- **その次:** エミュレーターの操作動画または画面記録から、開始・終了・後入力のタップ数とスクロール量を測り、画面を整理する。
- **その後:** 他のバックアップ形式への互換試験、分析指標の表示整理、公開ビルドを進める。

この順番で完了条件を満たした後、機種マスターの自動更新、仕事量の高度化、通知付きイベント、クラウド同期を再評価する。公開リポジトリで共同開発・再配布を受け入れる場合は、ライセンスを別途決める。
