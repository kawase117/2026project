## 1. 発端: 台選びの粒度

### 現行スキームの実態

`backtest/forward.py` の7ルールを台帳から読むと、7本中6本が無条件（entry_days なし）で、スコアが履歴平均のためピックが日々ほとんど動かなかった。`rakuen_jug_renovation_rb_top3` は4日間完全に同じ3台、`zassiki_jug_fixed_top3` は5日間完全固定。

つまり答えている問いが「**この店で恒常的に良い台はどれか**」であって「**今日どこに設定が入るか**」ではなかった。

### 粒度の4軸

議論の結果、混ざりがちな軸を分離した:

1. 推定の粒度（ホール / フロア / 区画 / 機種 / 位置属性 / 個別台）
2. 実行の粒度（結局1台）
3. 時間の粒度（恒常 / 条件付き / 当日状況依存）
4. コミットの粒度（打つ/打たないのゲート、どのホールへ行くか）

現行は 1 と 2 を両方「個別台」に揃えており、3 が実質固定、4 が存在しなかった。

### ユーザーからの重要な訂正

- **「実弾」→「実践」** の言い換え（`is_dry_run` の対義語として使っていた）
- **Top3は検証用サンプルであって実践用リストではない**。実践用は既に `recommendation-output-format-notion` instinct に「台番号順TOP50、埋まっていたら次の候補」として構築済みだった。私の「Top3では足りない」という指摘は**車輪の再発明**
- **高設定は10%程度**は業界の強めのイベントの平均的表現であり絶対基準ではない。優秀店（最近の楽園蒲田、かつての蒲田7）は高水準
- 目標は「朝から晩まで打って勝てる＝高設定台を見抜く」こと。逐次意思決定エンジンを作ることではない

## 3. 実装1: `eda/model_edge_briefing.py`

5.2MBのCSVをホール別1画面に要約する。DBには触らず既存CSVを読むだけ。

```bash
venv\Scripts\python.exe eda/model_edge_briefing.py --hall 楽園
```

### 判定フラグ

- `◎ 安定` … CI下限>0 かつ上位3台除外後もプラス
- `○ 少数台` … CI下限>0 だが上位3台を除くと消える
- `△ 要観察` … CI下限0以下

### 途中で見つけた自分の欠陥: 部分撤去を検出できなかった

初版は素の `edge_pp` 順に並べたため、n=2〜3のノイズが上位を占めた。既定を「撤去済み・n<8を除外、判定順→edge_pp順」に修正。

さらに**ARROWのビッグドリーム THE GOLDEN PUSHER が edge_pp +10.43・CI下限+8.44・上位3台除外後+9.39 と全ホール最大**だったが、実データを見ると:

- ARROWのホール全体は毎日320台記録されており、データ欠損ではない
- ビッグドリームは **20260702を最後に641-660のうち16台が撤去**、残ったのは650-653の4台のみ
- 台別上位の649(+3447)・643(+3328)・647(+3288)は、いずれも**7/2の1日しかデータが無い撤去済み台**
- CSVは `active_until_month_end=True` / `n_machines=20` と表示（コホートの一部が生き残ると撤去判定をすり抜ける）

**対処**: `coverage = n_machine_days / (n_machines × n_days)` を追加し、0.7未満は自動で△に落とす。全658行の中央値は1.00に対しビッグドリームは**0.23**。同じ検査でヒロキのいざ！番長(+4.77、稼働率0.36)も偽物と判明。

## 6. 蒲田7の差枚/104率乖離 → 測定ノイズだった

蒲田7は差枚で+0.554なのに104率は+0.117nsという乖離があった。仮説A（少数の大きな日に依存）と仮説B（104率の測り方の問題）を切り分けた。

**結果は仮説B**。台×日の104率は少回転日（100回転でも1件）に汚染されていた。**台×月**に集計し直すと:

| ホール | 台×**日**の104率 | 台×**月**の104率 |
|---|---:|---:|
| 蒲田7 | +0.117 (p=.16) ns | **+0.380 (p=2e-06)** |
| みとや | +0.222 (p=.028) | **+0.432 (p=9e-06)** |
| 楽園 | +0.319 (p=2e-06) | +0.172 (p=.012) |

「数日で大きく勝つ」説も否定。上位1/3の**勝日率**は蒲田7 52.6% vs 下位1/3 36.7%（+15.9pp）で、日単位で広く上回っていた。

### 設計ミスの記録

`top3_day_share`（月間エッジのうち上位3日が占める割合）という指標を設計したが、下位1/3は `monthly_edge_sum` の中央値が-2000〜-3000でゼロを跨ぐため、比率の分母が壊れて中央値15.7という無意味な値になった。**この列は解釈に使えない**。勝日率が正しい判別指標だった。

### 楽園だけ逆（日次>月次）の理由は未解明

カテゴリ仮説（JUG中心 vs AT中心）を立てたが**外れた**。楽園はAT・JUG両方で日次が強く、蒲田7・みとやは両方で月次が強い。月内前半→後半の104率相関はどのホールもほぼゼロ（0.02〜0.15）だったが、日次機械割SDがJUG 9.5pp・AT 24〜33ppあり、半月10日程度では検出力不足で判定不能。

回転数によるノイズ説も否定（楽園はAT回転数/日が最少1,868なのに日次シグナルが最強）。

## 7. イベント日定義の全ホール棚卸し

### きっかけ

楽園で「イベント日のほうが104率が9〜13pp低い」という異常な結果が出た。ユーザーから「楽園のイベント日は何度か調べたはずだがInstinctにないか」と指摘され確認したところ、`rakuen_theory.md` §3.1a に**カテゴリ別の確定定義**が既にあった。

### 判明した構造: 定義が3箇所に分裂、うち1つが劣化版

| 所在 | 内容 |
|---|---|
| `eda/core.py` の `is_x_day` | DDリスト OR 月末 OR 強ゾロ目（3条件OR、暦を見た動的な月末判定） |
| `eda/section_lateral_expansion.py` の `HALL_CONFIGS` | `event_dds` + `strong_zorome`。4ホールのみ収録。楽園は正しい |
| `eda/briefing_common.py:175` | `is_event_dd = df["dd"].isin(event_digits)` ← **DDリストのみ。月末も強ゾロ目も落ちる** |

**このセッションの分析3本はすべて `briefing_common` 経由**だったため、月末と強ゾロ目が非イベント日に混入していた。

さらに `HALL_EVENT_DIGITS` 自体の欠落: みとや `{4,7,14,17,24,27}` で運用定義の `1,30` が欠落、楽園 `{11,22}` で確定定義の `10,30` が欠落。

### 楽園の再検証結果（正しい定義で）

| 区分 | 新定義(10,11,22,30+強ゾロ目) | 旧定義(11,22のみ) | 誤報告した値 |
|---|---:|---:|---:|
| JUG | **+2.76pp** | +4.17pp | -10.7pp |
| HANA | **+2.66pp** | +3.39pp | -12.7pp |
| AT一般 | **+2.37pp** | +2.40pp | -9.1pp |

楽園の最強イベント日DD30が非イベント日側に入り、非イベント日の水準を押し上げていたのが原因。

ジャグ限定日DD{5,15,25}も理論どおり再現: JUGのみ+5.56pp、他4カテゴリはマイナス（HANA-2.83pp等）。

## 9. 自己訂正3: 手法依存で結果が変わった

9ホール分のtheory文書に機種内残差法の結果を記録した**後**、事前登録の準備でカテゴリ平均残差法（基準=同期間の同カテゴリ平均）を前後半に分けて計算したところ、**蒲田7で再現しなかった**。

| 手法 | 蒲田7 JUG 上位 | 蒲田7 AT一般 上位 |
|---|---|---|
| 機種内残差・全期間 | 1, 31, 30, 14 | 6, 30, 8, 16 |
| カテゴリ平均残差・前後半とも+ | **1,7,11,17,21,27,30,31** | **7,8,11,16,17,27,30** |

カテゴリ平均残差で見ると、**現行の `HALL_EVENT_DIGITS["蒲田7"]` はJUGについて9個中8個が前後半ともプラス**でむしろよく機能している。「現行定義は半分以上マイナス」という私の報告は機種内残差法に固有の結果だった。

蒲田7は期間中に72%の台が機種変更されており、機種内残差法は入替交絡を除ける反面、在籍の短い機種でDD別セルが薄くノイズを拾う。**どちらが正しいかは未決着**。

## 12. 実装3: `eda/event_calendar.py`

ホール×カテゴリ×status のイベント日定義を1箇所に集約。

### 構造

```python
EVENT_CALENDAR: dict[str, HallEventCalendar]
  └ by_category: dict[str, CategoryEventProfile]  # カテゴリ別カレンダーを持つホール
  └ shared: CategoryEventProfile | None           # 持たないホール（蒲田7）
```

`CategoryEventProfile` = `event_dds` / `status` / `source` / `measured_period` / `use_month_end` / `use_strong_zorome` / `note`

### status による足切り（このモジュールの肝）

- `confirmed` … 事前登録+フォワード、または独立2手法で再現済み。本番で使ってよい
- `watching` … 事前登録済みだが結果待ち
- `unconfirmed` … 探索スキャンで見えただけ。**本番の特徴量に使わない**

`is_event_day(date, hall, category, min_status="confirmed")` が既定で `confirmed` しか通さない。

### 登録状況

| ホール | status | 理由 |
|---|---|---|
| 楽園 JUG/AT一般/HANA | `confirmed` | §3.1a確定済み、今日別経路で再現 |
| 蒲田1 JUG | `watching` | 事前登録済み・結果待ち |
| 蒲田7(shared) | `unconfirmed` | 7系が主軸と実測、事前登録は未実施 |
| ARROW/ヒロキ/ザシティ/金時/レイトギャップ/みとや | **未登録** | 単一手法・全期間平均のため書かない |

### 既存への影響ゼロ

`eda/core.py` の `HALL_EVENT_DIGITS`（27ファイル参照）は**一切変更していない**。移行は問題判明済みの経路（`briefing_common`）から個別に行う方針。
