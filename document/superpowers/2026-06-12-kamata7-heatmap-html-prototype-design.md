# 蒲田7ヒートマップ HTML試作デザイン

## 目的

`dashboard/pages/page_17_heatmap.py` の現行 `Plotly go.Heatmap` 表示を、提示画像のような「台カードをフロア上へ並べる見た目」に近づけたい。

ただし、いきなり本番の `page_17_heatmap` を置き換えるのではなく、まず `Heatmap/` 配下に単体HTMLの試作を作り、本当に成立するかを確認してから本体へ統合する。

## 背景

現行実装は [heatmap_common.py](C:/Users/apto117/Documents/pachinko-analyzer/src/2026project/Heatmap/heatmap_common.py:118) で `go.Heatmap` を使っており、台ごとの値を「色付きのマス」として描いている。

この方式には次の限界がある。

- 台ごとの枠線、文字組み、カード余白を細かく制御しにくい
- 通路や島の大きな余白を「見た目として自然に」表現しにくい
- エスカレーターやフロアラベルのような装飾要素を画像風に置きにくい
- 提示画像のような「台番号 + 機種名のカード」を主役にした表現と相性が悪い

そのため、試作段階では `Plotly` の装飾ではなく、`HTML/CSS` によるカード配置へ切り替える。

## 試作対象

試作対象ホールは `マルハンメガシティ2000-蒲田7` とする。

理由は以下のとおり。

- `2F` と `3F` の2フロア構成で、単純な1枚マップより難しい
- 島の本数、段差、通路余白が複雑で、座標ベース描画の成立確認に向いている
- ここで成立すれば、より単純なホールへ横展開しやすい

入力データは既存の以下をそのまま使う。

- `Heatmap/2F_floor_coordinates_kamata7.csv`
- `Heatmap/3F_floor_coordinates_kamata7.csv`
- `db/マルハンメガシティ2000-蒲田7.db`

## 成果物

試作段階の成果物は `Heatmap/` 配下の単体HTML生成スクリプトと、その出力HTMLとする。

この試作では、`page_17_heatmap` 本体は変更しない。既存ユーザー導線を壊さず、見た目と技術成立性だけ先に評価する。

想定成果物:

- `Heatmap/generate_kamata7_html_card_map.py` のような試作生成スクリプト
- `Heatmap/kamata7_card_map_preview.html` のような出力HTML

ファイル名は実装時に既存命名と整合させるが、責務は「蒲田7のカード型フロアマップ試作」を明確に分けることを優先する。

## 描画方式

### 採用方式

`HTML/CSS` による絶対配置のカード描画を採用する。

各台を1つのカードとして表現し、`display_x` と `display_y` をカード配置座標へ変換する。フロア全体は相対配置コンテナとし、その上に各台カードを `position: absolute` で並べる。

### 採用理由

- 台カードの背景色、枠線、角丸、フォントサイズを自由に制御できる
- 島間や通路の大きな余白を自然に表現しやすい
- エスカレーターのような非台要素をHTMLブロックとして追加しやすい
- 後で `Streamlit components.html()` に埋め込みやすい

### 非採用案

`Plotly go.Heatmap` の継続利用は非採用とする。理由は、見た目の自由度が不足し、今回の目標である「カード型フロアマップ」への到達に対して回り道になるため。

`SVG` は有力な代替案だが、試作1本目ではHTML/CSSの方が実装速度と調整容易性で有利なため後回しとする。

## 表示内容

### 試作1本目で表示する情報

各台カードには最低限以下を表示する。

- 台番号
- 機種名の短縮表示
- 色分けされた背景

初回試作の色指標は `平均差枚` を採用する。

理由:

- 赤系の濃淡が提示画像の印象に近い
- 正負や強弱がユーザーに直感的に伝わりやすい
- `平均G数` や `勝率` よりカード着色の見栄えを作りやすい

### 色表現

初回は連続色スケールよりも、画像寄りのカード見た目を優先する。

想定する色帯:

- 強いプラス: 濃赤
- 弱いプラス: 薄赤
- 中立: 白
- 弱いマイナス: 薄青または薄グレー
- データ欠損: グレーアウト

この段階では厳密な統計意味より「視認性」と「元画像の表情への近さ」を優先する。

## コンポーネント構成

試作は次の3責務に分ける。

### 1. Data Loader

責務:

- SQLite から `machine_detailed_results` を読み込む
- 指定期間の台別集計を行う
- `平均差枚` を中心に、将来拡張しやすい形で `勝率` と `平均G数` も返せるようにする

要件:

- 日付範囲を指定できる
- 台番号ごとに1行へ集約する
- データが存在しない台は `NaN` のままレンダラへ渡す

### 2. Layout Mapper

責務:

- `2F_floor_coordinates_kamata7.csv` / `3F_floor_coordinates_kamata7.csv` を読み込む
- `display_x` / `display_y` をカード配置座標へ変換する
- 将来の他ホール横展開を見据えて、`display_x` / `display_y` があればそれを優先し、なければ代替列へフォールバックできる形にする

要件:

- 2Fと3Fを独立に扱える
- 座標欠損があれば明示的に検出する
- フロアの幅・高さを座標の最大値から決定する

### 3. HTML Renderer

責務:

- フロア単位のコンテナを作る
- 台カードを絶対配置で並べる
- 色、枠線、タイポグラフィ、余白を制御する
- 2F/3F を同一HTML内に並べる

要件:

- 現行 `Plotly` より明確に画像寄りの見た目であること
- 機種名は省略しても台番号の可読性を優先する
- 余白とカードサイズをCSS変数で調整できること

## データフロー

1. 座標CSVを読み込む
2. DBから指定期間の台別実績を集計する
3. 座標と実績を `machine_number` で結合する
4. フロアごとにカード配置用の中間データへ整形する
5. HTML文字列を生成する
6. 単体HTMLとして保存する

試作段階では、この流れを1本のスクリプト内で完結させてよい。ただし、将来 `page_17_heatmap` へ統合しやすいよう、関数境界は責務ごとに分ける。

## 試作で確認する成功条件

試作成功の判定は以下とする。

1. 蒲田7 `2F/3F` の複雑形状でも、台カードが破綻なく配置される
2. 現行 `go.Heatmap` より、提示画像に近い視覚印象を出せる
3. 既存の座標CSVと既存DBだけで生成できる
4. データ欠損台や未知機種名があっても描画自体は止まらない
5. 試作が失敗しても `page_17_heatmap` 本体は無変更で安全に残る

## フォールバックとエラーハンドリング

- 座標CSVが見つからない場合: 明示的な例外で停止
- DBが見つからない場合: 明示的な例外で停止
- 実績データが空の場合: HTML生成を中止し、理由を返す
- 機種名が長すぎる場合: 省略表示する
- 指標値が欠損している場合: グレー表示にする

試作では「完全自動修復」より「どこが壊れたか分かる失敗」を優先する。

## `page_17_heatmap` への移行条件

以下を満たした時点で、本体統合を検討する。

- 単体HTMLの見た目がユーザー要求に十分近い
- 2F/3F の複雑座標で崩れない
- 色分けルールが実用上許容できる
- `Streamlit components.html()` または同等手段で埋め込み可能な見込みが立つ

統合時の方針:

1. まず `page_17_heatmap` に試作表示タブを追加して並行比較する
2. 問題がなければ既存 `Plotly` 表示を置き換えるか、フォールバックとして残す

この順にすることで、直接置き換えによる回帰リスクを避ける。

## 検証方針

試作段階の検証は以下に絞る。

- 生成HTMLをブラウザで目視確認する
- 2F/3F の配置崩れがないことを確認する
- データ欠損台がグレー表示されることを確認する
- 長い機種名がレイアウトを壊さないことを確認する

この段階ではスナップショットテストや広範な自動テストより、見た目と配置の成立確認を優先する。

ただし、将来統合前には「座標CSV読込」「台別集計」「HTML断片生成」の最小限ユニットテストを追加できるよう、関数は分けて設計する。

## スコープ外

今回の試作では以下を扱わない。

- 全ホール対応
- 既存 `page_17_heatmap` の即時置換
- 末尾ハイライトとの統合
- 高度な凡例UIやインタラクティブフィルタ
- 完全な画像一致

目的はあくまで「蒲田7でカード型フロアマップが成立するか」を確認すること。

## 推奨実装順

1. 蒲田7の座標CSVとDBを読む最小スクリプトを作る
2. 台別 `平均差枚` 集計を返す
3. 2Fのみでカード配置を試す
4. 3Fを追加して同一HTMLへ統合する
5. 色帯、文字、省略ルールを調整する
6. HTML出力を固定化し、目視レビューできる状態にする
7. その後に `page_17_heatmap` 統合プランへ進む

## 結論

`page_17_heatmap` の見た目改善は、現行 `Plotly heatmap` を直接拡張するより、蒲田7を使った `HTML/CSS` カード型試作を先に成立させる方が技術的に妥当である。

この試作が成立すれば、既存の座標CSV資産を活かしたまま、フロアマップ表現を段階的に本番へ移せる。
