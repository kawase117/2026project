# 予測の手順(「◯日の予測」を作るとき)

CLAUDE.md から移した(2026-10-30)。予測の形は `document/reviews/2026-10-monthly-retrospective.md` の4節A・B・Eに基づく。

## 0. 最初に読む

1. `document/registry/LESSONS.jsonl` — 確認済みの学び。判断行の根拠が、ここにある「効かない型」(前日の継続・少台数機種・過去回3回以下など)だけになっていないかを見る。凍結時に機械点検もかかる。
2. 対象ホールの `memory/halls/<ホール>.md` — ホール固有の規則・申告・注意。
3. 予告があるホールは `backtest/announce/` の当日分。未登録の予告を見つけたら、予測より先に `EVENTS.md` の手順で登録する。

## 1. 予測の形(2026-10-30 から)

- **各ホールの最初に、基準 `*_model_term60_top3`(直近60日の機種平均上位3)の3機種をそのまま載せる。** 手書きは「基準との差」だけ書く。予告・イベントで差し替える機種にだけ理由を書く。
  - 根拠: 10月は手書きの推しが基準とほぼ同成績(楽園 +329 対 +324)。差し替えが当たらないなら、手書きをやめて基準だけにする(11月末に判定)。
- **蒲田7は、予告のない日に機種を推さない。** 鉄台2026と、RB判別機の自動候補だけ載せる(10月の手書きは −182、プラス29%で全ホール最悪)。
- **「避ける」は構造の理由だけで書く。** 機械割の低さ・稼働不足(打たれない)・設置台数の変化。前日・過去回の負けを理由にしない(10月の開店前「避ける」は −130)。
- **台番号の名指しは `backtest/rb_candidates.py` の自動候補に一本化する。** 手で台を選ぶのは、予告で台が指定された日だけ(10月の手書き名指しは −414)。
- **予告がある日は、筆頭名指し・公約機種・先バレを主にする。** 同系列の過去回は従(`event-day-replay` スキル)。言葉遊びから機械的に拾った機種は判断行に入れない。
- 予告がないホールは、基準3機種+ジャグラー候補(下記)+RB自動候補だけでよい。
- 判断行は少数にとどめ、文書を短く保つ(10月後半に文書が3倍になったが、精度は上がらなかった)。
- 候補には「事前の文献根拠あり」か「当日その場で発見」かを書き分け、効果量にはCI幅を併記する。

## 2. ジャグラー候補(2026-10-30 改定、ユーザー了承済み)

コマンド: `venv\Scripts\python.exe -m backtest.juggler_carryover tomorrow --hall <ホール名> --top 10`。結果を予測文書の「ジャグラー候補」節に表で入れる。

| ホール | 扱い | 根拠(10月の差枚edge) |
|---|---|---|
| みとや | **毎回出す(継続)** | +461(16日)、有効 |
| 楽園 | **11月末まで毎回出す**。11月末に差を検出できず平均 +100 以下なら止める | −59(16日)、プラス31% |
| 蒲田7 | **候補表を出さない。**「ジャグラー候補は出さない(10月は有害、差枚edge −141・95%CI上限 −15)」と一行書く | −141(15日、CI −351〜−15) |
| 蒲田1 | 予告にジャグラー強化がある日だけ出す(従来どおり) | +151(10日)、RB比は −0.104 |
| 雑色・金時東口・金時京急・ヒロキ東口・平和島・ARROW | 「ジャグラーの設定5以上の割合が低く、候補を出さない」と一行書く | 割合5%台以下(10/12推定) |

- 変更の経緯: 2026-10-13 に「設定5以上の割合が高いホール(蒲田7・楽園・みとや)で毎回出す」と決めた(仮説 `jug-cand-high-share-halls`)。10月の採点で、割合の高さと候補の当たりは結びつかなかった。割合は機種全体の話で、持ち越し候補で台を選べることとは別。
- 割合が低いホールは、判定の直前に直近60日で推定し直し、5%を超えたら候補表に戻す。
- 蒲田7の凍結forward(`backtest/forward/*_jug_*__<日付>.json`)は朝の自動処理で採点用に残る。予測文書の表には入れない。
- 既定はana-sloのDB最終日の確定データ(スナップショット不要)。営業中スナップショットを使うときだけ `--snapshot`。
- DBが対象日の前日まで取り込まれていないときは、その旨を書く。黙って省略しない。
- 手順と注意は `document/JUGGLER_SETTING_PATTERNS.md`(冒頭「必須手順」。[監査]行を引用し、予測力は弱い=約14%対無作為10%と明記)。

## 3. 書式と凍結

- 推す機種は「判断:」の行、避ける機種は「避ける」を含む行、ジャグラーは「ジャグラー候補」の表(見出し行・区切り行・列数を守る)。この3か所だけが機械的に抜かれ、翌朝採点されて `backtest/forward/SCOREBOARD.md` に載る。
- 「判断:」「避ける」の行に、読みの説明で別機種の名前を書かない(10/23、軸の機種が避ける側に凍結された)。
- 凍結前に `venv\Scripts\python.exe -m backtest.prediction_ledger extract document/reviews/<日付>-prediction.md` で抜き出しを確かめる。
- **開店(10:00)前に** `venv\Scripts\python.exe -m backtest.prediction_ledger freeze-doc document/reviews/<日付>-prediction.md` で凍結する。凍結後に文書を直しても台帳は変わらない。
- 凍結が LESSONS の点検で止まったら、行を直す。どうしても通すときは `--allow L00x:理由`(理由は凍結JSONに残る)。
- 予告のclaimsは、登録済みなら直接編集せず `backtest.announce amend` を使う。
