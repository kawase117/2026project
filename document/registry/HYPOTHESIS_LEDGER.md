# 仮説レジストリ（追記専用）

> **目的**: 「疑問に思った→検証した→どうだったか」を1件1行で全件保持する。不成立も同格で残す。
> **性質**: 追記専用。行は削除しない。結論が変わったときは判定列を書き換え、`後継` に新しい id を書く。
> **参照方法**: このファイル1本を読めば、そのホールで何が既に問われたかが分かる。詳細は `出典` へ。
> **最終更新**: 2026-08-06（フォワードテスト監視を全9ルールに拡張。判定点が未記載だった4本に停止規則を固定。蒲田1・みとや・楽園・雑色の節を新設）

## 判定値

| 判定 | 意味 | 質問は閉じたか |
|---|---|---|
| `成立` | 効果があり、現在も有効と考えている | 閉 |
| `期間限定成立` | 特定期間では実在した。期間外は不成立または未検証 | 期間内は閉 |
| `失効` | **当時は本物だった。ある時点で効かなくなった。** 死亡日を記録する | 閉（ただし復活監視の対象） |
| `棄却` | 実用上意味のある大きさの効果は無いと言える。CIが実用閾値を挟まない | 閉 |
| `棄却(プールのみ)` | 全期間プール／omnibus検定でのみ null。**レジーム粒度・top-k粒度では未決** | **開** |
| `帰無-検出力不足` | 効果が無いのではなく、あっても分からない。CIが広い | **開**（データ増で再検証） |
| `検定不能` | 比較単位に重なりが無い等で、そもそも定義されない。有意/非有意の話ですらない | 定義されない |
| `撤回` | **測定・定義そのものが誤っていた。効果の有無とは無関係。** | 閉（再測定が必要なら別idで） |
| `上書き済み` | 後続の検証で結論が置き換わった。`後継` を参照 | 後継へ |

**`失効` と `撤回` を混ぜないこと。** 撤回は「我々が間違えていた」、失効は「ホールが変えた」。
後者だけが「過去に発動していた法則」として価値を持ち、失効日の集まりはレジーム変化の検出器になる。
無関係な複数の法則が同じ時期にまとめて失効していれば、それはホール側の方針変更である。

## 期間の扱い

- **どの判定も期間を伴わなければ意味を持たない。** `有効期間` 空欄は「未記入」であって「全期間」ではない。
- **外部情報で事前に切った期間**（改装・店長交代・増台・レジーム宣言）は多重性を持ち込まないので、区間内の検定をそのまま信用してよい。
- **データから見つけた期間** は `成立` にしない。ホール×軸×窓の組み合わせは膨大で、純ノイズでも必ず「最も良く見える窓」が存在する。`backtest/forward/LEDGER.jsonl` のフォワードで買うこと。
- 生死の継続監視は `backtest/deathwatch.py` + `backtest/deathwatch/claims.json` が担う（判定: ALIVE / WEAKENED / DEAD / REVERSED / STRENGTHENED / UNDERPOWERED / NO_BASELINE）。本レジストリはその上位の索引。

### 端番効果の台数構造（`rk-clean-edge1-*` を読む前に必ず見ること）

「端」は3段階の絞り込みの結果であって、フロアの端の総数ではない。本館2Fの例:

```
141台（フロア全体）
 → 32台  端(depth=1)      … 16列 × 両端
 → 18台  clean列に限定     … frame(外周6列12端) と special(1列2端) を除外（§2.1c）
 →  3台  技術介入に限定     … 残り15台はAT一般
```

|---|---|---|---|---|

| 本館1F | 15 | 82 | 20 | 0 |

| フロア | AT一般 | ジャグ | 技術介入 | 計 |
|---|---|---|---|---|
| 新館1F | 10 | 0 | 0 | 10 |

読み方の要点:

- **カテゴリとフロアがほぼ完全に分離している。** ジャグは本館1Fのみ、技術介入は本館2F・3Fのみ、
  新館は全台AT一般。**新館に技術介入機は1台も無い**ので、新館での端番効果は
  「関与していない」のではなく **検定不能**（[[feedback-statistical-certainty-calibration]]、
  および §1 の本館↔新館が検定不能だった理由と同根）
- 技術介入の端14台のうち **本館2Fは3台**。しかもそのうち2台は 2152-2162（スマスロハナビの島）の
  両端で、実質1島の話。本館2Fの技術介入端番はこの規模で測っていた
- **clean列の端70台のうち48台（69%）はAT一般で、§2.1c はAT一般では端番効果を非有意
  （-0.113pp）としている。** 端の多数派では効果がなく、少数派カテゴリでのみ効果が見えていた形。
  カテゴリで割らないと効果が消え、割ると n が十数台になる——という構造的なジレンマがある
- ハナハナは clean列の端が **0台**で検定不能。**⚠️ 上表は工事前(2026-04)の配置。工事後は
  ハナハナ16台が本館1F(1100-1129)から本館3F(3166-3175, 3176-3181)へ全移動し、
  2列とも `frame`（外周）になった。** frameは投入単位として機能しない（§2.1c）ため今後も測れない
- ⚠️ **この表自体が工事前スナップショットである。** 工事(2026-07-06)でカテゴリの
  フロア配置は変わっている。現在の配置を論じるときは必ず `date >= 20260706` で取り直すこと

⚠️ したがって `rk-clean-edge1-*` の失効は「16か月安定した頑健な発見が死んだ」というより
**「もともと十数台で測っていた薄い発見が続かなかった」** と読むほうが実態に近い。

## フォワードテスト監視・横断の注意（2026-08-06）

- **多重比較**: 現在 9 本が並走している。各ルールの合格条件は「95%CI 下限 > 0」（片側 2.5%）なので、**全部が無効だとしても少なくとも1本が合格する確率は約 22%**（1 − 0.975⁹）。個別ルールの合格をもって「有効な手法を見つけた」と結論してはならない。合格が出た時点で、そのルールだけを対象に**新しい期間で再度フォワードする**こと。
- **ルール間は独立でない**。同一ホール・同一カテゴリのルールがしばしば同じ台を選ぶ（例: 2026-08-05 の `k7-fwd-jug-hit104` と `k7-fwd-jug-rb` は共に台3175 を選出し、その +2,490 が両方の成績を作っている）。ルール横断で「n勝m敗」と数えると水増しになる。
- **正規近似CIは判定に使えない**。日次系列は同一台が連日入るため系列相関があり、iid 仮定の標準誤差は過小になる。判定は各行に書いた 7日ブロックブートストラップで行うこと。本レジストリに併記している正規近似CIは**現状把握のための参考値**であり、合否判定には用いない。
- **判定点に到達する前にルールを畳まないこと**。2026-08-06 に「成績の悪い4本を畳む」案が出たが、これは事前登録が防ごうとしている当のふるまい（optional stopping）そのものである。畳んでよいのは各行に書いた n に到達し、事前に決めた検定で不合格になったときだけ。

**土曜日についての注意（2026-08-29）**

ユーザーの事前見解「強めのイベント日＋土曜日なので、ある程度強い入れ方をすると考えている」に対し、
**稼働を統制すると土曜はむしろ薄い**。2026-04以降147日の OLS で **土曜ダミー -1.82 (p=0.003)・日曜 -2.39 (p<1e-4)**。
土曜の生の閾値超え平均 4.55（全曜日最高）は、土曜の稼働（台あたり平均4,423G、全曜日最高）で完全に説明され、
稼働1,000Gあたり +1.6機種という係数を当てはめると土曜は「稼働から期待される水準を約1.2機種下回る」。
解釈としては、土曜は放っておいても客が来るので設定で呼ぶ必要が薄い、という向き。
**予測時に「土曜だから強い」を根拠に使わないこと。** 使うべきは稼働の推定値（動員予想・午前の入り）であって曜日ではない。
