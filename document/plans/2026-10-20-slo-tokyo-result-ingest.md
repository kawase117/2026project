# slo_tokyo「結果速報」の取り込み設計(機種名・カテゴリ別)

作成 2026-10-20。設計のみ(実装は未着手)。根拠の数字は、`scraper/twitter_monitor/state.db` の `slo_tokyo` 全文37件(2026-10-05〜10-19)と、各ホールDBの確定値による実測。

## 1. 目的と前提

- 蒲田1・蒲田7・ヒロキMAX・ヒロキ東口の「結果速報」を、本文から **機種名×カテゴリ** に分けて取り込み、答え合わせ(機械集計)で使えるようにする。
- 既存の取得元(999999Q9Q の画像をOCR)に比べ、機種名の引き当て率が100%対56%、蒲田7の10/15〜10/18は既存に0件(検証済み、2026-10-20)。**テキストなので画像OCRは使わない。**
- 既存の仕組み `backtest/result_corpus.py`(`external_result_reports` / `external_result_models` / `external_result_machines` を `db/analysis_results.db` に作る派生データ)に**乗せる**。新しい保存先は作らない。

## 2. 本文の文法(実測)

```
2026-10-18 マルハンメガシティ2000蒲田7 ｜結果速報      ← 1行目: 営業日(年つき)・ホール名・固定語「結果速報」
■日曜日                                              ← 曜日/日付の特徴(■で始まるが括弧の件数が無い行)
▶割切リサーチ                                        ← イベント名(▶で始まる行)。無い日もある
全体平均+310枚                                       ← ホール全体の平均差枚(枚/台)
ピック18.0%(129/715)                                 ← 発信者独自の「ピック」の割合と台数
並び84人 (オンライン抽選288人)                          ← 抽選人数(東口・MAXにある)
▶ ポイント / ✅日曜日 / ※機種イチ                      ← 発信者の注記(取り込まない、raw_textに残す)
■ 全系(2機種)                                        ← セクション見出し: ■ 名前(N 単位)
・戦国乙女5 業火を穿つ宿焔の双刃                         ← 箇条書き = 1機種 または 1箇所
■ 2台並び(11箇所)
・スマスロ ハナビ〜アレックス                           ← 並びは「A〜B」(機種Aから機種Bへ続く並び)
■ その他(21台)                                       ← 件数だけで箇条書きなし
```

**自己検算に使える性質:** 見出しの(N機種/N箇所)と、直下の箇条書きの数が、96セクション中96で一致した(不一致0)。箇条書き424件のうち36件が「〜」を含む。同じ(日,ホール)の重複投稿は37件中0件。

**見出しの語彙(実測):** 全系(2機種) / 全(1機種) / 1/2(8機種) / 列1/2(5箇所) / 3台並び・5台並び(N箇所) / 単品(6箇所) / 特定箇所仕掛け(2箇所) / 優秀以上(22箇所) / 末尾⑦1/2(39台) / 末尾⑤(AT機)(17台) / 末尾③(ノーマル機)(17台) / 角④(AT機)(20箇所) / 角②(ノーマル機)(12箇所) / 列全 / N台並び全 / パネル全 / 取材対象 / その他(N台)。

**⚠️ 絵文字🌈はDBの本文から落ちている。**Xのページの `inner_text` に絵文字が出ないため、「全🌈」は「全」、「単品🌈」は「単品」として保存されている。🌈の有無で意味が違うかは、取り込み側からは区別できない(未解決事項1)。

## 3. 保存先(既存テーブルへの追加)

> **実装時の変更(2026-10-20):** 既存の `external_result_*` を読む箇所が `result_corpus.py` の外に5つあった(`event_days.py`、`integrated.py`、`monthly_report_layer2.py`、`seven_d_results.py`、テスト)。これらは全行を「ホール公表の結果」として読むので、同じ表に `slo_tokyo` を入れると、発信者の判定(東口の全🌈など)が公表と取り違えられる。そのため**同じDB(`db/analysis_results.db`)に別テーブル `poster_result_reports` / `poster_result_models` を作った**(`backtest/result_corpus.py` の `build_poster`、コマンド `python -m backtest.result_corpus build-poster`)。既存の読み手は一切変わらない。以下の列の案のうち、`label_semantics` は不要になった(表の分離で代替)。実装した列は `backtest/result_corpus.py` の `POSTER_SCHEMA` を正とする。ピックの合算(`pick_units_sum`)は、検算の参考値として保存するだけで、`parse_ok` には使わない(蒲田1・蒲田7の16件中、完全一致は7件、残りは「角」「末尾」の数え方などで数台ずれる)。

`external_result_reports` に追加する列(`build()` と同じ「既存DBへの後付けALTER」の流儀で通す):

| 列 | 意味 |
|---|---|
| `label_semantics` | `hall_published`(ホール自身が公表した該当台。既存の slokotae7 行はこれ)/ `poster_judgement`(発信者の判定。slo_tokyo はこれ)。**既定値は `hall_published`**。 |
| `hall_mean_diff` | 「全体平均」(ホール全体の平均差枚)。既存の `target_mean_diff`(対象台の平均)とは別物。 |
| `parse_ok` | 検算(§5)が全部通ったか。通らなければ0にして取り込み、集計側で落とせるようにする(黙って捨てない)。 |
| `text_complete` | 本文が全文か(`full_text` あり、または切れていない)。 |

`external_result_models` に追加する列:

| 列 | 意味 |
|---|---|
| `granularity_raw` | 見出しの名前そのまま(例: `全系`、`2台並び`、`末尾⑤(AT機)`)。 |
| `model_parts` | 箇条書きを「〜」で分けた機種名のJSON配列(`["スマスロ ハナビ","アレックス ブライト"]`)。全系・1/2などは1要素。 |

既存の列の使い方:`model_name` には箇条書きの**原文**を入れる(原文を残す)、`mean_diff`・`n_target`・`n_total`・`number_from/to` は、`slo_tokyo` の本文に無いので NULL。

**ピック%** は `target_machines` / `total_machines` / `target_pct` に入れてよいが、`label_semantics='poster_judgement'` で区別する。ピックは差枚や機械割の固定の閾値では再現できなかった(2026-10-20検証)ので、「ホール公表の該当台」と同じ列に混ぜて集計してはいけない。

## 5. 検算(自己検証。通らなければ `parse_ok=0`)

1. **件数検算:** 各セクションの見出しの(N機種/N箇所)と、箇条書きの数が一致する(実測96/96)。単位が「台」のセクションは箇条書きが無くてよい。
2. **日付検算:** 1行目の年つき日付の曜日と、本文の `■日曜日` などの曜日が一致する(既存の `weekday_ok` と同じ扱い)。
3. **全文検算:** `full_text` が無く、`tweet_text` が120字以上のときは `text_complete=0`(取り込まない)。実測では、取得した67件は全件が途中で切れていた(§7)。
4. **ホール名検算:** 1行目のホール名を、DB名へ対応づける表で引く。引けないホールは `is_tracked_hall=0` で取り込む。対応表:`ヒロキ蒲田東口店`→`ヒロキ東口店`、`ヒロキMAX蒲田店`→`ヒロキMAX蒲田店`(西口は対象外)、`マルハンメガシティ2000蒲田1/蒲田7`→`マルハンメガシティ2000-蒲田1/蒲田7`。
5. **全体平均の検算:** 「全体平均」とDBの当日平均の差を記録する(実測:蒲田1・蒲田7は±3枚以内、MAX・東口は+12〜16枚DBが高い)。ホールごとに許容を決め、外れたら警告。
6. **機種名の引き当て:** 箇条書きの機種名を、当日DBの機種名に引き当てる(先頭の `L`/`LB`/`S`、空白、記号を除いて照合。実測107/107=100%)。95%未満なら警告。

## 6. 取り込みの流れ(`result_corpus.py` への追加)

- 新しい解析関数 `parse_slo_tokyo(text, posted_at)` → `(header, models)`(`parse_report` と同じ戻り値)。
- 新しい定数(`RESULT_ACCOUNTS` と並べる): `BULLET_ACCOUNTS = {"slo_tokyo": {"halls": {...対応表...}}}`。
- `build()` の「1投稿を書き込む処理」を関数に切り出し(`_store_report`)、`RESULT_ACCOUNTS` と `BULLET_ACCOUNTS` の両方から使う。べき等:`INSERT OR REPLACE`(report_id=tweet_id)、`DELETE` してから `external_result_models` を挿入。
- 同じ(source, ホール, 営業日)が複数あれば、最新の投稿を残す(実測は重複なし。将来の訂正投稿に備える)。
- **派生データなので、毎回 `state.db` から作り直せる**(既存の `build()` の設計と同じ)。

## 7. 収集側の変更

- 巡回は `config.py` の `ACCOUNTS` に追加済み(未コミット)。`run_daily.py` の `collect` は全アカウントを巡回する。
- **全文の取り直しを `slo_tokyo` にも効かせる:** `run_daily.py` の `HALL_KEYWORDS`(ホールを名指しする語)に、東口・MAX・蒲田1・蒲田7の語が入っているか確認し、足りなければ足す(`fetch_full_text.py` は `HALL_KEYWORDS` に載ったホールしか取り直さない)。

## 8. 下流への接続

1. **答え合わせの機械集計(`scripts/run_morning_docs.py` / `morning_facts.py`)に1節を足す。** `slo_tokyo` の全台・1/2・並びに挙がった機種が、当日DBで実際に何台中何台プラスか、平均差枚、ホール平均との差を、機械で出す(蒲田1・蒲田7・MAX・東口)。実測では、蒲田7 10/18 の「全系 戦国乙女5」が24台で平均+4,762・勝率83%、蒲田1 10/17 の「全系」4機種が13台で平均+4,023・勝率100%だった。
2. **`result_corpus.stats()` と `propagate_granularity()` は変えない。** ただし、**`WHERE label_semantics='hall_published'` を明示的に足す**(既存行は既定値で `hall_published` なので、挙動は変わらない)。足さないと、発信者判定の「全🌈」(東口には差枚マイナスの1台機種が入る)が、`stats()` の「本物の全台系の分布」に混ざる。
3. **台番号への結び付け(`external_result_machines`)は、この段階ではやらない。** `slo_tokyo` の本文には台番号が無い。並び(A〜B)を配置(`machine_layout`)の隣接から台番号へ戻すのは、段階2の検討事項。
