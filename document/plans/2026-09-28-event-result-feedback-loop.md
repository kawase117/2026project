# イベントの答え合わせを次の予測に戻す仕組み（設計書）

- 作成: 2026-09-28
- 状態: 設計案（実装前）
- 相談: Codex と壁打ち済み（read-only）。ユーザー回答 3 点を反映済み

## 1. 目的

次の流れを、毎回手作業で思い出さなくても回るようにする。

```
Xで予告を集める
  → 予測する
  → 翌朝: アナスロ実績DBが入る
  → 数日〜30日後: 主催者の結果発表が出る
  → 両方を、元のイベントに結びつけて保存する
  → 次に同じイベントが来たら、過去の回の結果を1枚の表で出す
  → それを見て予測する
```

## 2. 前提にする考え方（ユーザーの問題認識）

1. ホールの設定の入れ方は短い期間で変わる。長く効く法則を探すより、直近の回の結果を次に使う方が役に立つ。
2. ただし、前月までに設定が多く入った機種などの「ここ1〜2か月の傾向」も重要。
3. 同じイベントの過去の回の中身と答え合わせが、一番重要な材料。
4. 結果発表は2週間以上遅れて出ることがあるので、後から来たものを正しく元のイベントに付ける必要がある。
5. 差枚などの数値だけでなく、主催者の答え合わせラベル（マイナスで終わった台にも設定が入っていたか等）が重要。

長期のルール検証（`backtest/forward.py`）は今のまま残す。役割は「ルールを採用するか捨てるか」の判断に限る。
この設計が作るのは「次の予測に入れる材料」であり、ルールの採否には使わない。
過去の回は数件しかないので、そこから法則を言い切らない。

## 4. 全体の形

新しく作るのは「台帳2つ」と「コマンド2つ」だけにする。既存の台帳・DBのスキーマは変えない。

```
[既存] EVENT_DAYS.jsonl ─┐
[既存] announce/*.json ──┤（予告の公約 claims）
[既存] state.db ─────────┤（ツイート本文・画像の台番号）
[既存] analysis_results.db external_result_* ─┤（結果発表: 報告×機種×台）
[既存] db/<ホール>.db ───┘（実績）
          │
          ▼
[新] EVENT_SERIES.jsonl … 「同じイベント」のまとまりの定義と、各回の所属
[新] EVENT_RESULT_LINKS.jsonl … 各回と結果発表の結びつき（後から追記）
          │
          ▼
[新コマンド] event_days.py series / link   … 候補を出す・確定を記録する・未結びつきを出す
[新コマンド] event_days.py history <ホール> <日付> … 過去の回の答え合わせ表を出す
```

- 新しい台帳は追記だけの JSONL にする。訂正は上書きせず、`supersedes` で前の行を指す新しい行として足す。
- 実績DB・`external_result_*`・予告JSONには書き込まない。表は毎回読み取って組み立てる。
- `event_days.py` のサブコマンドとして足し、新しいモジュールは増やさない（結合処理は `backtest/integrated.py` の関数を再利用する）。

## 5. 部品1：「同じイベント」をまとめる（EVENT_SERIES.jsonl）

### まとめ方（ユーザー決定）

同じイベントかどうかは、次の4つで判断する。

1. **ホール名**（必須。違うホールは混ぜない）
2. **イベント名**（表記ゆれを吸収して比べる）
3. **公約**（予告が約束した内容。例: 「末尾7の1/2」「北斗 1/3」「3台並び」）
4. **先バレ元**（予告を出したアカウント。例: kawasakislot、999999Q9Q）

まとまりは2種類持つ。

- **名前のまとまり**：同じホール・同じ名前のイベント（例: 楽園の「スロトレ調査団」）
- **公約のまとまり**：同じホール・同じ公約（例: 楽園の「末尾7の1/2」。イベント名が違っても同じ公約なら同じまとまり）

1つの回が、名前のまとまりと公約のまとまりの両方に入ってよい。

### 公約の揃え方

公約は予告JSONの `claims` から作る。形をそろえた短い文字列（公約キー）に変換する。

| claims の type | 公約キーの例 |
|---|---|
| `position_rule`（末尾・角番など） | `末尾:7:1/2` |
| `model_named_ratio` | `機種指名:1/3`（機種名は入れない。機種は回ごとに変わるため） |
| `model_named` | `機種指名:全` |
| `zentaikei_count` | `全台系:N機種` |
| `narabi`（新設。下記） | `並び:3台` |

機種名を公約キーに入れないのは、「毎回どの機種が指名されるか」自体を過去の回から見たいためである。指名された機種は表の列として出す。

### 並びの公約を予告の登録形式に足す（ユーザー指摘により確定）

並びはよく使われる公約で、楽園では予告49件中24件の本文に出てくる（蒲田1は13件中5件、ヒロキ東口は2件中2件）。
それなのに `backtest/announce.py` には並びの公約の種類も採点も無く、今は本文やメモにしか残っていない。

- `claims` に `{"type": "narabi", "n_adjacent": 3, "count": 20, "scope": "ホール全体" | 機種名}` の形を足す（`count` は「◯か所」。書かれていなければ null）。
- 採点は既存の並び検出を使う。差枚の連続だけでなく、回転数の連続（G比2以上・自台30日比1.5以上）でも見る。
- 報告される「◯か所」は通常日でも多い（楽園の通常日の中央値18〜34か所）ので、か所数の達成は的中として数えない。表には、材料で裏付けられたか所数を出す。
- 既存の予告JSONは書き換えない。新しい種類は今後の登録から使い、過去の回は本文から読み取った並びを、表示のためだけに別の欄に出す（凍結済みの予告の中身とハッシュは変えない）。

### 決め方の段階（ユーザー決定）

1. **最初は候補を出してユーザーが決める。** コマンドが候補を点数付きで出し、ユーザーが「同じ／違う」を答える。答えは `decided_by: user` として記録する。
2. **自動に切り替える条件**：直近20件の候補で、自動判定とユーザーの答えが19件以上一致したら、そのホールは自動で決める（`decided_by: auto`）。
3. 自動で決めたものも、一覧でいつでも見直せるようにし、ユーザーが違うと言えば `supersedes` で訂正する。

### 行の形（例）

```json
{"row_id": "s-0001", "series_id": "rakuen_kamata__name__sutoretoru_chosadan", "axis": "name",
 "hall": "楽園蒲田店", "label": "スロトレ調査団", "aliases": ["スロトレ調査団三大天", "調査団"],
 "event_id": "20260915_楽園蒲田店_スロトレ調査団三大天2日",
 "decided_by": "user", "decided_at": "2026-09-28T15:00:00+09:00", "supersedes": null}
```

## 6. 部品2：結果発表を後から結びつける（EVENT_RESULT_LINKS.jsonl）

### 結びつけ方

- 鍵は **(ホール名, 営業日)**。投稿日（`posted_at`）とは分けて持つ。
- 探す先は2つ。
  1. `external_result_reports`（取り込み済みの結果発表）
  2. `state.db` の投稿（まだ取り込んでいない結果発表を探す。当該ホールのアカウントが、営業日から45日以内に投稿したもの）
- 1つの回に発表が複数来ても（速報・詳細・訂正）、全部残す。代表を1つ決めて `primary: true` を付け、訂正版は前の発表を `supersedes` で指す。

### 状態

| 状態 | 意味 |
|---|---|
| `linked` | 結果発表が見つかり結びついた |
| `multiple_candidates` | 候補が複数あり、どれか決められない（ユーザー確認待ち） |
| `waiting` | まだ見つからない。営業日から45日以内 |
| `not_found` | 45日たっても見つからない。発表が無かったとみなす（設定が入らなかったという意味ではない） |

### いつ照合するか

毎朝の定例（`scripts/run_morning.py`）の最後に、`waiting` の全件を照合し直す。
Codex からは「3日後・7日後・30日後」の案が出たが、件数が少なく照合は軽いので、毎朝全件の方が単純で漏れない。

### 過去分の探索（ユーザー決定: 探す）

結果の無い過去の回（約81件）は、一度だけまとめて探す。

1. `state.db` の既存の投稿から探す（新たな収集は不要）
2. 見つかった発表は `backtest/result_corpus.py` の既存の取り込み処理にかける
3. それでも見つからない回は一覧にして、`scraper/twitter_monitor/backfill_search.py` で追加収集するかをユーザーに聞く

## 7. 部品3：過去の回の答え合わせ表（`event_days.py history`）

次のイベントの前に、1枚の表で出す。

### 対象

- 指定した回と同じ **名前のまとまり** の過去の回
- 同じ **公約のまとまり** の過去の回
- 並びは新しい順。件数は固定しない（ユーザー決定: 「3回前」は目安）。既定では、体制変化（店長交代・改装）より後の回をすべて出し、変化より前の回は区切り線の下に薄く出す。
- **予測の時点より後に分かった情報は出さない。** `--asof` を指定すると、その時点までに投稿された結果発表だけを使う（後から答え合わせを再現するため）。

### 表の中身（1回につき1ブロック）

**回の見出し**：日付・曜日、イベント名、先バレ元、公約、結果発表の有無と遅れ（日数）

**機種・台ごとの行**：

| 列 | 中身 | 出どころ |
|---|---|---|
| 台番号 | 当時の台番号 | 結果発表・実績DB |
| 当時の機種 | その日にその台番号に入っていた機種 | 実績DB |
| 今の機種 | 今その台番号に入っている機種。違えば「入替」と表示 | 実績DB の最新日 |
| 区分 | JUG / BT / A+AT / AT | machine_master |
| 予告で指名 | その回の予告に名前が出ていたか | announce JSON |
| 主催者ラベル | 全 / 1/2 / 1/3 / 並び / なし | external_result_models・machines |
| 差枚・回転数 | その日の実績 | 実績DB |
| 判定用の数値 | ノーマル系は RB 確率（機種の普段の値との比）、AT 機は機種単位の G比×平均差枚 | 実績DB |
| 一致の分類 | 下の5分類 | 計算 |
| 現場の報告 | 演出での設定確定・現地組の報告（あれば） | 部品4 |

**一致の分類**（数値とラベルが食い違っても消さない）：

1. ラベルあり・差枚プラス
2. ラベルあり・差枚マイナス（**不発台。重要**）
3. ラベルなし・差枚プラス（ラベルの付け漏れか、設定と関係ない勝ちか。区別できない）
4. ラベルあり・実績DBに台が無い
5. 粒度が合わない（例: 機種単位の「1/2」で、どの台か分からない）

**回の下の集計**：ラベル台数、そのうちマイナス台数、指名機種の的中（既存の `announce.py score` の結果をそのまま表示）

### 表の最後に付けるもの（ここ1〜2か月の傾向）

- そのホールの直近30日・前月の「設定が多く入ったとみられる機種」上位。既存の `announce.py named-context` の集計を再利用し、新しい計算は作らない。
- 過去の回で繰り返し出た機種・台番号・末尾（2回以上出たものだけ）。何回中何回かを必ず併記する。

### 台番号と機種の扱い

- 過去の実績は **今の台番号で引く**。機種名で引くと、入替前の別機種の実績が混ざる（楽園の北斗・カバネリ・からくりサーカス2で実例あり）。
- 入替があった台は「当時は別の機種」と表示し、機種の傾向の集計からは外す。
- Codex は機種の系統ID（シリーズ・世代をまたぐID）を新しく作る案を出したが、採らない。手間に見合わないため。

## 8. 部品4：現場の報告を残す

演出での設定確定や現地組の報告は、数値より確かな場合があるので残す。

- 置き場所：`backtest/field_obs/field_obs.jsonl`（新規・追記だけ）
- 1行の中身：ホール、営業日、台番号または機種、報告の中身（例: 「設定5以上確定」「全」）、情報源の種類（本人が打って確認／現地組の伝聞／SNS）、報告者、登録日時
- 実績の数値と食い違っても両方残す（例: 9/27 楽園モンハンライズは現地組が「全」、DBは9台中5台プラス）。
- 予告としては登録しない（結果を知ってからの情報なので、的中率が必ず100%になる）。

### 情報の重み（ユーザー決定）

演出で設定を確認した報告は、主催者のラベルより重く扱う。重い順に次のとおり。

1. **演出での設定確認**（本人または現地で打った人が確認したもの）
2. **主催者の結果発表ラベル**
3. **現地組の伝聞**（「全」だった等。台ごとの確認ではない）
4. **実績DBの数値**（ノーマル系のRB確率、AT機の機種単位の成績）

答え合わせ表では、この順で「その台に設定が入っていたか」の判断を出す。上の情報がある台は、下の情報と食い違ってもその判断を採り、食い違いがあったこと自体は印として残す。
例: 9/27 楽園エウレカ3227 は差枚-714 だが、演出で設定5以上を確認済みなので「入っていた」と判断する。
なお、演出の確認は「設定5以上」「偶数」など範囲で示されることが多いので、範囲のまま記録し、6と決めつけない。

## 9. やらないこと

- 他ホールの結果発表を、当方ホールの配置の法則として混ぜない。
- 結果発表・店長の結果投稿を予告として登録しない。
- 結果発表が無い回を「設定が入らなかった回」として扱わない。
- 差枚だけで設定の有無を判定しない。
- 実績DBのスキーマを変えない。
- 過去の回の件数が少ないうちは、「法則」として言い切らない。表には必ず「何回中何回」を出す。

## 11. Codex に渡す単位

段階1〜5をそれぞれ1回の依頼にする。どの依頼にも次を必ず書く。

- Python は `venv\Scripts\python.exe`、`PYTHONUTF8=1`。`db/pachinko.db` は0バイトのダミー。実績は `db/<ホール名>.db`
- 実績DB・`external_result_*`・予告JSON・`EVENT_DAYS.jsonl` の既存行に書き込まない。新しい台帳は追記だけ
- 鍵は (ホール名, 営業日 YYYYMMDD JST)。投稿日と営業日を混ぜない
- ホール名は実績DBのファイル名と同じ表記にそろえる（`scraper/twitter_monitor/hall_aliases.py` を使う）
- ノーマル系は RB 確率、AT 機は機種単位の G比×平均差枚。合算（BB+RB）は使わない
- 新台（導入0〜6日）は印を付けて表示する（除外しない）
- `--asof` より後の情報を使わないことをテストで確かめる
- テストは `test/` に置き、`venv\Scripts\python.exe -m pytest test/ -v` が通ること
