# ダッシュボード再構築プラン（2026-07-10）

> **目的**: 散発的なテストページの寄せ集めになっているダッシュボードを、
> 「セオリーの実証」と「新たなセオリーの発見」という本来の2つの用途に沿った構成へ再編する。
> **決定済み方針**: Phase 1→2→3→4 の順で全フェーズ実施 / セオリー・クレームは新規YAMLレジストリで管理 /
> 効果なし確定の単一軸ページは1ページに統合。
> **関連**: `kamata7_dashboard_implementation_plan.md`（旧・蒲田7専用ページ実装計画。本プランのPhase 2で汎用化して吸収）

---

## 背景（現状診断）

- 22ページ・約6,500行。`main.py` の手書きルーターと `config/constants.py` の
  `PAGES` / `PAGE_REGISTRY` が二重定義。
- ページの役割（探索 / セオリー検証 / 運用 / 管理 / テスト）が未分類で並列に並んでいる。
- セオリー検証は蒲田7専用ページ（20〜22）のみ。theory文書は9ホール分あるため、
  現行パターンの踏襲は9×3=27ページ増で破綻する。
- `utils/kamata7_theory.py` に `THEORY_COVERAGE_ROWS` / `refutation_warnings()` として
  セオリー内容がコードに直書きされ、`document/kamata7_theory.md` と二重管理。
- instincts の知見では単一軸（曜日・第X曜日・日末日など）は全ヌル確定。
  シグナルは交互作用（セグメント×DD×角番等）にあるが、現行ページ群は単一軸中心。
- EDA（`eda/` の機種×DD/曜日横断スキャン等）で実際に発見が出ているのに、
  その手法がダッシュボードに還元されていない。

## Phase 1: 骨格整理（低リスク・即効）

1. **ページレジストリ統一**
   - `constants.py` の `PAGES` と `PAGE_REGISTRY` を単一のレジストリに統合。
   - 各エントリ: `key / title / icon / group / render / visible`（`visible=False` でテストページを隔離）。
   - `main.py` のルーター辞書はレジストリから自動生成。
2. **サイドバーのグループ化ナビ**
   - 上記4グループ構造で表示。`st.radio` のフラット一覧を廃止。
3. **単一軸ビューアへの統合**
   - 対象: page_02（日別）, 03（曜日別）, 05（末尾別）, 06（日末日別）, 07（第X曜日別）, 09（台番号末尾別）。
   - 軸セレクタ＋共通の集計/グラフ描画1ページに統合。データ目視確認の用途は維持。
   - 集計ロジックの共通化は `utils/` に集約（フィルタは必ず `utils/filters.py` 経由）。
4. **テストページ隔離**
   - page_19（Visual Test）を `visible=False` に。`old-dashboard.py` は削除候補として棚上げ。

**完了条件**: ナビが4グループ表示になり、既存機能がすべて到達可能。統合前後で集計値が一致。

## Phase 2: セオリー検証フレームワークの一般化（本丸）

1. **セオリー・クレームYAMLレジストリ新設**
   - 置き場: `document/theory_registry/<hall>.yaml`（instincts と同様の運用）。
   - theory.md 本体は手動管理ルールを維持。レジストリは「検証対象のインデックス」であり、
     theory文書の自動生成には使わない（feedback-theory-docs-must-be-hand-authored 準拠）。
   - スキーマ案（値は例）:
     ```yaml
     hall: kamata7
     claims:
       - id: k7-3fln-dd7-12-tail9
         title: 3F_L_N × DD7-12 × 末尾9 は構造シグナル
         status: robust        # robust | fragile | refuted | watching
         segment:              # 検証対象の絞り込み条件（宣言形式）
           floor: 3F
           lr: L
           family: N
           dd: [7, 12]
           machine_tail: [9]
         metric: hit104_rate   # avg_diff | win_rate | hit104_rate ...
         direction: up
         baseline: hall_all    # 比較対象
         min_n: 5
         source: document/kamata7_theory.md#該当セクション
         last_reviewed: 2026-07-03
     ```
2. **ホール別セグメント設定の外出し**
   - `dashboard/config/hall_configs/<hall>.yaml`（または .py）に
     フロア判定・L/R判定・A/N機判定・冷却帯・鉄台・イベント日定義を移設。
   - `utils/kamata7_theory.py` の関数群を `utils/theory_engine.py`（汎用）＋ hall_config 参照に分解。
   - イベント日定義は確定版（7のつく日+1のつく日+ゾロ目+強ゾロ目MM=DD+月末、鉄台=台番号2026）を正とする。
3. **汎用セオリー検証ページ（1枚）**
   - ホール選択 → レジストリのクレーム一覧 → クレームごとに標準検証ブロックを描画:
     全期間 vs 直近90日 の指標、n、効果量、比較グラフ、status バッジ。
   - 旧 page_20/21/22 はこのページに吸収して削除。
4. **セオリー健全性チェックページ**
   - 全ホール×全クレームの「直近90日でまだ生きているか」を一覧（劣化の早期検知。3F_N初敗北のようなケースを拾う）。

**完了条件**: kamata7 の既存3ページの内容が汎用ページで再現でき、
最低もう1ホール（例: mitoya か kamata1）のクレームが同じページで表示できる。

## Phase 3: 発見支援ページの新設

1. **交互作用エクスプローラ**
   - 任意の2〜3軸（セグメント/DD/角番/末尾/イベント日/機種ファミリ）のクロス集計マトリクス。
   - 効果量・p値・期待セル数警告・min_n ガードを標準装備（significance-test-design instincts 準拠）。
   - 有望セルから「レジストリにクレーム下書きを追加」する導線（YAML スニペット出力）。
2. **横断スクリーニングページ**
   - `eda/` の機種×DD/曜日スキャン（machine_axis_pattern_scan 系）をUI化。
   - ホール選択 → 全機種スキャン → 有意結果ランキング。90日ウィンドウ再現性チェック付き。
   - 「粗く網羅 → 細かく限定」の第一段をダッシュボードで回せるようにする。

## Phase 4: クリーンアップ

- 吸収済みページ（02,03,05,06,07,09,20,21,22）と `old-dashboard.py` の削除。
- `utils/` の未使用関数整理、theory_engine / registry ローダーのユニットテスト追加。
- CLAUDE.md / document のページ一覧記述を更新。

## 実装上の注意（既存ルールの継承）

- フィルタは必ず `utils/filters.py` を使う（ページ内インライン実装禁止）。
- min_games フィルタは集計**前**に個別台レベルで適用。
- SQL属性は `ALLOWED_ATTRIBUTES` ホワイトリスト検証を維持。
- 新台は games_normalized 分析から除外（shindai-exclude instinct）。
- ホール横断のプール分析は提案しない（各ホール独自戦略が前提）。
- Plotly 複合軸は `make_subplots()` 方式。
