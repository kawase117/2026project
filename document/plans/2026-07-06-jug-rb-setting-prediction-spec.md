# ジャグラーRB確率ベース設定予測 — Codex実装仕様書

作成: 2026-07-06 / 設計: Claude / 実装担当: Codex
背景: `document/superpowers/2026-07-06-signal-ceiling-variance-decomposition.md`

## 目的

RB回数（二項分布に従う唯一のクリーンな設定信号）だけを使い、
**翌日にどの台が高設定（設定4以上）になるか**をホール別に予測・評価する。

## スコープ

- **対象ホール（優先順）**: 蒲田7、蒲田1、（余力があれば ARROW池上・レイトギャップ平和島・みとや大森町）
- **対象外**: 金時・ベルシティ・ヒロキ（分散分解で日次設定シグナル≈0を確認済み。実装しないこと）
- **対象機種**: machine_name に「ジャグラー」を含む台のみ
- 差枚（diff_coins_normalized）は特徴量にも評価にも**使用禁止**（打ち切り内生性でバイアスするため）

## データ規約（厳守）

- DBパスは引数で受け取る。デフォルト `db/マルハンメガシティ2000-蒲田7.db`（カレントは 2026project ルート想定）
- テーブル `machine_detailed_results`: `date` TEXT "YYYYMMDD" / `machine_number` INTEGER / `machine_name` TEXT / `games_normalized` INTEGER / `rb_count` INTEGER / `bb_count` INTEGER
- `to_markdown()` 使用禁止（tabulate未導入）。出力は print + CSV
- 空セグメントの集計は NaN になる — 必ず件数ガードを入れる
- フィルタ: games_normalized >= 500、新台除外（(台番,機種)初出現から7日、ホール初日から存在するペアは除外しない）、蒲田7は date末尾"0707"と台番2026を除外

## Stage 2: 台×日 設定事後分布

`stage2_daily_posterior.py`

```
π_it(s) ∝ prior_hall(s) × Binom(rb_count | G, p_s^RB) × Binom(bb_count | G, p_s^BB)
```

- prior_hall(s): ホール×機種系統ごとにEMで推定（全台×日の混合二項フィッティング、6成分固定）。
  EMが不安定なら一様事前でも可（その場合レポートに明記）
- 出力（CSV, 台×日）: `date, machine_number, machine_name, G, rb, bb, p_set1..p_set6, p_high(=P(s>=4)), e_setting, e_payout`
- サニティチェックを必ず出力: (a) 全期間平均の p_high がホール常識的範囲（1〜25%）か、
  (b) G が大きい日ほど事後が尖っているか、(c) 蒲田7の7/7を除外できているか

## Stage 3: 特徴量（すべて予測日より前の情報のみ。リーク厳禁）

`stage3_features.py`。台×日（予測対象日）ごとに:

- `b_machine_90d`, `b_machine_180d`: 過去90/180日の p_high 平均（James-Stein縮小: 全台平均へ n/(n+20) で縮小）
- `p_high_lag1`, `p_high_lag2`: 前日・前々日の p_high（据え置きシグナル）
- `days_since_high`: p_high>0.5 だった直近日からの経過日数（上限30でクリップ）
- `high_freq_same_weekday`: 同一曜日に限った過去 p_high 平均
- カレンダー: 曜日、日末尾、is_zorome、is_strong_zorome、is_month_end、is_month_start
- 蒲田7のみ: イベント日フラグ（7のつく日 OR 1のつく日 OR 日ゾロ目(11,22) OR 強ゾロ目(月=日) OR 月末）

## Stage 4: Walk-forward評価

`stage4_walkforward.py`

- 学習: 直近180日 → 翌1ヶ月を予測、月次ロール（既存 `ml/experiments/walkforward_scoring/` の流儀に合わせる）
- モデル: LightGBM binary（目的変数: 当日 p_high > 0.5）と、単純加算スコアの両方
- **ベースライン階層（必須）**:
  - B0: ランダム選択
  - B1: `b_machine_180d` のみで順位付け
  - B2: B1 + カレンダー係数（線形）
  - M: フルモデル
- 評価（日ごとにジャグ台を順位付け→Top3選択）:
  - `mean_p_high_top3`: 選択台の当日実現事後 p_high の平均（主要指標）
  - `spearman`: 予測順位 vs 実現 e_setting 順位
  - `payout_lift_pp`: 選択台の実現 e_payout 平均 − ホールジャグ平均
- 有意性: 日単位の moving block bootstrap（block=7日, 2000回）で M−B1 の差の95%CI
- 出力: `results/` に CSV + サマリテキスト。**M が B1 に有意に勝てない場合はその旨を結論に明記**（negative resultも成果）

## 判定基準（先に固定）

- M > B1 が有意 → 日次動態（据え置き・イベント）に予測価値あり → 実運用スコアラーへ
- M ≈ B1 → 台効果ランキングのみ運用（それでも価値あり）
- B1 ≈ B0 → 該当ホールのジャグ台選択に構造なし（分散分解の結論と照合）

## 実装順序

1. Stage 1 + 機種名一覧の確認出力（**ここで一度停止し、機種マッピングをレビューに出す**）
2. Stage 2 + サニティチェック
3. Stage 3-4
4. 蒲田7 → 蒲田1 の順で実行

テストは `test/ml/` に最低限: 二項尤度の手計算一致、リーク検査（特徴量日付 < 予測日）、新台除外の境界。
