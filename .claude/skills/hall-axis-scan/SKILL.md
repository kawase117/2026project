# ホール軸総当たり(hall-axis-scan)

## 目的と原則

**目的**: 過去データから、高設定投入の**候補**を、**漏れを確認できる形**で洗い出す。見つかったものは候補で、確定ではない(勝率30%は負ける。事後の推定は開店前に分からない)。

- **指示を待たない。** 軸を1つずつ頼まれて出すのではなく、最初の報告に、下の軸カタログ全体の結果(完了・データ不足・失敗・未実施とその理由)を入れる。黙って落とさない(`hall-analysis-checklist` と同じ約束)。
- **ホールごとに回す。** ホール間で共通の法則はほぼない。別ホールの結果・実施状況・数値を、このホールの結果として使わない。ホール別ファイル(`references/<ホール>.md`)は、**仮説の候補を出す材料**としてだけ読み、当たりとして引き継がない。
- **一度の長い出力を網羅性の証明にしない。** 網羅は、台帳と、軸ごとの結果ファイルの照合で示す。
- 「検出できなかった」と「ない」を混ぜない。1水準が3〜12日だと、数%〜十数%は拾えない。検出力(検出できる最小の効果)を軸ごとに書く。

## 0. 開始時の確認(分析に入る前に必ず)

次を確認し、台帳のヘッダに記録する。確認できない項目は「不明」と書き、その軸は「データ不足」にする。

| 項目 | 確認内容 |
|---|---|
| ホール | 正式名、`db/<ホール>.db`。**そのホールの** `references/` ファイルの有無(あれば読むが、結果は引き継がない) |
| 期間・基準日 | DBの最小・最大日(基準日=最大日)。欠測日(連続日付の穴)の一覧と、休業か欠測かの区別(区別できなければ「欠測」) |
| 分析期間 | 直近3か月を主、レジーム境界以降、全期間(下の「期間の取り方」) |
| レジーム境界 | **先に既存の履歴から候補日を抽出する**: `machine_layout_history` の `valid_from` の変更日(改装・配置替え)、機種の初出日・消滅日(入替。`mr.load_first_seen`)、台数の急変日。**それでも判断できないとき(店長交代・運営方針の変更など、DBに残らないもの)だけ、ユーザーに聞く。** 抽出した候補日と、使った根拠を台帳のヘッダに書く。配置履歴は、全ての配置替えを持つとは限らない(例: 楽園は版が2つで、9/7・9/14の変更は履歴にない)ので、履歴にない境界は、機種の初出・消滅と台数から確かめる。台数・台番号が変わる機種は、前後を混ぜない |
| 台日表 | `machine_detailed_results`(日、機種、台番号、回転数、差枚、BB、RB)。G=0の行の扱いを記録(履歴軸では欠測理由として残す) |
| 配置 | `machine_layout_history`(セクション、角番)。なければ位置軸はデータ不足 |
| 機種マスター | 設定別のRB確率があるか。`backtest/bonus_specs.py` の `load_specs(hall=...)` |
| RB列が使えるか | 機種ごとの確認(下の「指標」)。**ホール別の** `document/registry/AT_RB_AUDIT.csv` の行の有無 |
| イベント台帳 | `EVENT_DAYS.jsonl`・`EVENT_SERIES.jsonl`・`PAST_PROMISES.jsonl` のそのホールの行。なければ、イベント・公約軸はデータ不足 |
| 祝日 | DBの `is_holiday` は誤り(全ホール、2026-09-14)。`jpholiday` で作る |

## 1. 実行台帳

分析の最初に、**カタログの全軸**を「未実施」で並べた台帳を作る。

置き場所: `output/axis_scan/<ホール>__<基準日>/LEDGER.csv`、軸ごとの結果は `results/<axis_id>.json`。

```
axis_id,axis,unit,metrics,window,status,scope,planned,done,excluded,basis,runner,result_file,reason,updated
```

| 列 | 内容 |
|---|---|
| axis_id | カタログのID(T1, H2, L1, V1…)。単位・指標で分けるときは `H2:machine:G` のように枝番をつける |
| status | **未実施 / 完了 / データ不足 / 失敗**(この4つだけ) |
| scope | **実行範囲**。「全組み合わせ」と書くときは、軸数・水準数・単位数・指標数・セル数を書く |
| planned | **実行前に確定する予定セル数** = 単位の数 × 指標の数 × 期間(窓)の数 × 水準の数。実行を始める前に書き、結果を見てから変えない |
| done | 結果を出せたセル数(全セル結果ファイルの行数) |
| excluded | 除外したセル数(日数・台数の不足、計算不能など)。全件を除外ファイルに理由つきで残す |
| basis | `as_of`(基準・分位・候補選定・客数補正が、すべて対象日より前のデータだけ。当日実績を使わない。開店前に使える)/ `ex_post`(基準・分位・選定は対象日より前だが、客数補正に当日実績を使う。事後分析)/ `in_sample`(期間全体で基準を作った説明用)。下の「未来データを使わない規則」 |
| runner | 使ったモジュール・関数、または「使い捨て(scratchpad/…)」 |
| reason | 未実施・データ不足・失敗は**必須**。未実施の理由(検出力・事前仮説なし・手段なし・時間)、データ不足の中身(日数n、欠測)、失敗の例外1行と再実行の可否 |

状態の意味:

- **完了**: 次の**すべて**を満たす。
  1. `planned = done + excluded`(予定したセルが、結果か除外のどちらかに全部入っている)。
  2. 全セル結果ファイルの行数 = `done`、除外ファイルの行数 = `excluded`。除外には理由コードがある。
  3. 必須の項目(`planned`・`done`・`excluded`・`n_days`・`cells_file`・`excluded_file`・`basis`)が null でない。null を許すのは、その軸に当てはまらない項目だけで、`caveats` に理由を書く。
  4. `top` の全候補が、全セル結果ファイルに存在する。
  **一部の単位・指標・期間だけ実行したものは、完了にしない**。出せた分は結果ファイルに残し、状態は「失敗」(理由に「一部のみ n/N」)か「データ不足」にする。
- **データ不足**: 必要なデータがない、または日数・台数が最小に満たない。不足の内容を書く。
- **失敗**: 実行したが、例外や不整合で結果が出ていない。
- **未実施**: まだ回していない。「後で」は理由にならない。理由(手段が未実装、検出力が足りない、事前仮説がない、など)を書く。

### 結果ファイルの固定形式

軸ごとに、**3つのファイル**で保存する。JSONは要約と所在で、全結果ではない。

- `results/<axis_id>.json`: 要約(下)
- `results/<axis_id>.cells.csv`: **全セルの結果**(1行=1セル: 単位、水準、指標、期間、日数n、効果、区間、p、q、族、`basis`)
- `results/<axis_id>.excluded.csv`: **除外したセルの全件**(単位、水準、指標、期間、理由コード)

```
{"axis_id":"", "hall":"", "asof":"YYYYMMDD", "window":"開始-終了", "status":"", "basis":"as_of|in_sample",
 "scope":"", "planned":0, "done":0, "excluded":0,
 "cells_file":"results/<axis_id>.cells.csv", "excluded_file":"results/<axis_id>.excluded.csv",
 "n_days":0, "n_units":0, "families":0, "cells":0,
 "p05":0, "p05_expected":0.0, "bh_q02":0,
 "top":[{"label":"", "metric":"", "n_days":0, "effect":0.0, "ci":[0.0,0.0], "q":0.0,
         "falsification":"済|未実施|該当なし", "next_month":"済|未検証|該当なし"}],
 "power":"検出できる最小の効果", "caveats":[""], "reason":""}
```

`top` は5件まで。`metric` は、回転数 / 差枚 / 機械割差(pt) / RB確率 / AT初当り率のどれかで、**1つの候補に指標ごとに1行**。差枚と機械割差は同じ出玉の証拠なので、2行に分けても**加点しない**。**RB確率とAT初当り率は別の指標・別の検定族**で、同じ行にも同じ族にも入れない。`falsification` は反証確認(F1)、`next_month` は翌月検証の状態。**翌月検証がまだできない候補は「未検証」と書き、報告でも「未検証」と明示する**(検証済みのように扱わない)。

### 最後の照合(統合報告の前に必ず)

1. カタログの全軸IDが台帳にある(ない=黙って落とした)。
2. 全行の状態が4つのどれか。未実施・データ不足・失敗には reason がある。
3. 「完了」の行には、`.json`・`.cells.csv`・`.excluded.csv` の3つがあり、完了の条件(1〜4)を満たす。
4. **件数の照合**: 台帳の `planned`・`done`・`excluded` と、JSONの値、2つのCSVの実際の行数が、すべて一致する。`p05`・`bh_q02` などの集計値が、`cells.csv` から数え直した値と一致する。
5. `results/` にあって台帳にないIDはない。
6. 統合報告に載せた候補・数値が、すべて `cells.csv` の行から引ける(統合時の見落としと転記ミスの検査)。
7. 統合報告の件数(状態別)=台帳の件数。

照合に合格しないものは、報告で「照合未了」と書く。**現状は照合の自動化がない**(下の「実行手段の現状」)。手で行うときは、上の7項目の結果を報告に書く。

### 組み合わせの範囲

- 「全組み合わせ」は、**2軸まで**を実行範囲とし、台帳の scope に数を書く。
- **3軸以上は、事前仮説がある場合に限る**(出所と登録日を scope に書く)。1水準が数日になり、総当たりでは検出力が尽きるため。
- 事前仮説のない3軸以上は、台帳に「未実施(事前仮説なし・検出力)」と書く。

## 指標

評価は、4つの指標で行う。**どの指標を出したか・出せなかったかを、台帳の metrics に書く。**

1. **回転数**: 客数補正後の期待回転数に対する比、および1台日の平均G。
2. **差枚**: `diff_coins_normalized`。回転数の違う台日を比べるのには使わない(差枚 ≈ 3×回転数×(機械割−1))が、**評価項目としては全機種で出す**。
3. **機械割**(出率): `100 + 100×差枚÷(3×G) [%]`。**表記を分ける**:
   - 「機械割」=その台日・群の出率そのもの(例: 104.2%)。
   - 「機械割差(pt)」=基準との差(例: +3.1pt)。**基準を毎回書く**(100%か、同機種・同回転数帯の平均か、ホール平均か)。
   - コードの「機械割」列(`Σ(差枚−期待差枚)÷Σ3G`)は**機械割差(pt)**。報告では機械割差と書く。
4. **RB確率**(**その機種・ホールのRB列が設定判別に使えると確認できた場合だけ追加**): RB回数÷総回転数。比較は、機種×回転数帯の基準から出した期待RB回数との比 O/E、または台日ごとのRB事後確率。
5. **AT初当り率**(AT機で、ホール別の監査で当り列が確認できた場合だけ追加): **RB確率とは別の指標・別の検定族**。

**差枚と機械割(差)は、関連する指標(同じ出玉の言い換え)。独立した2つの証拠として加点しない。** 候補の根拠は、「出玉系(差枚・機械割差)」「回転数」「RB確率」「AT初当り率」の4系統で数え、RB確率とAT初当り率は混ぜない。

### 機種カテゴリで、RB側・OTHER側に固定しない

- **差枚・機械割・回転数は、全機種で評価する。** ノーマル・BT・A+AT・ATのどのカテゴリでも、出玉系と回転数は必ず出す。
- **RB確率は、機種カテゴリで決めない。** 機種ごと・ホールごとに、次の4項目を確認できたものだけに追加する(ノーマル・BTも、A+ATも同じ)。**カテゴリ名(A+ATなど)や、過去のメモだけを根拠に、機種群をまとめてRB対象へ移さない。**
  1. RB列が空でない(`rb=0` かつ `bb>0` の機種は除く)。
  2. マスターに、設定別のRB確率がある。
  3. そのホールの実測が、マスターの設定1〜6の範囲に入る(ホールで列の意味が違うことがある)。
  4. 台日ごとのばらつき(分散比)が、二項分布から大きく外れない。
- **AT初当り率**: ホール別の監査(`backtest/at_rb_audit.py`、`AT_RB_AUDIT.csv`)でAの機種の当り列(bb / rb / bb+rb)は、**AT初当り**で、RB確率とは別の量。別の指標・別の族として出す。bb+rb合算の列は、そのホールの監査でその列だけが範囲に入る場合の例外。
- 台帳の metrics 列に、機種群ごとに、どの指標を出せたか(RB確率・AT初当り率を出した機種の一覧と、確認結果)を書く。

**現行コードとの食い違い**(下の「実行手段の現状」): 台日表の `seg` は RB/OTHER の排他で、カテゴリがノーマル・BTか監査済みATならRB側、それ以外(A+ATを含む)はOTHER側に固定している。RB側の機種は機械割差を、OTHER側の機種はRBを出さない。この方針とは**合わない**ので、要実装。確認項目(1)だけが実装されている。`backtest/bonus_rate.py` は、AT機をBB+RBの合計で扱い、RBの判別可否を見ない。

## 履歴軸(H1〜H6)

**目的**: 同じ台・機種・位置の、過去の挙動から、その日の高設定の投入が読めるか(繰越し、反動、数日おきの投入、直近の水準)を見る。

### 窓の定義(暦日、対象日 t)

| ID | 窓 | 暦日の結び方 |
|---|---|---|
| H1 | 前日 | t−1日 |
| H2 | 7日前 | t−7日(同じ曜日) |
| H3 | 14日前 | t−14日(同じ曜日) |
| H4 | 直近1か月 | [t−30日, t−1日] |
| H5 | 直近2か月 | [t−60日, t−1日] |
| H6 | 直近3か月 | [t−90日, t−1日] |

- **暦日で結ぶ。** 「7行前・14行前」(`shift(7)`)は、休業日・欠測日があるとずれるので使わない。`日付−timedelta(days=7)` の日付で結合する。
- **欠測と0Gを分ける。** 理由コードを残し、前後の日で埋めない。
  - **行がない**(ホールの行がない=休業または欠測、その台の行がない=未稼働・入替・DBの欠落): 全指標が欠測(NaN)。理由を休業 / DB欠測 / 台の行なし / 入替に分ける。
  - **記録された G=0**: **回転数の分析では有効な観測(0G)**で、平均・分位に含める(捨てると、稼働の分析が高回転側へ偏る)。**RB確率・機械割差・AT初当り率は、分母が0で計算不能**なので、その指標だけ対象外にする(NaN。除外ファイルに理由コード `G0` で残す)。
  - 窓の有効日数は、**指標ごとに**数える(回転数は0Gを含め、率の指標は含めない)。
- **移動窓は、対象日を含めない。** 窓は t−1日までのデータだけで作る。窓の統計(平均、分位)、機種×回転数帯の基準、客数補正、閾値の分位も、**対象日より前**(対象日を含まない)のデータだけで作る。規則の全体は「未来データを使わない規則」。
- 窓の有効日数(欠測を除く)を、特徴量と一緒に保存する。有効日数が、窓の日数の7割(台番号単位は10日)に満たないものは欠測にする(初期値。台帳に使った値を書く)。
- **単位**: 機種、台番号、位置(末尾・角番・島・列)。**指標**: 回転数、差枚、機械割差(pt)、RB確率(利用可能な機種)。
- **その単位自身の長期の水準を引いて見る。** 引かないと、日を問わず強い台(水準)を、履歴軸が再検出するだけになる。
- 結果は、当日の結果(指標)との関連(順位相関、または特徴量の上位/下位25%での差)と、順列検定(曜日の中での入れ替え)で出す。

## 高回転軸(V1)— 「大きく負けても高回転」

**必須の独立項目。** 設定の手がかりとして、回転数は、差枚とは別に見る。

### 抽出

- 台日で、**差枚が大幅マイナス**かつ**5000G以上**を抽出し、**6000G・7000G以上**でも同じ表を作る。
- 「大幅マイナス」の閾値(初期値: 差枚≦−2000枚、または機械割差≦−10pt)は、**分析の開始時に台帳に固定**し、結果を見てから動かさない。
- 差枚の代わりに機械割差で切る版も並べる(回転数が違うと、差枚の閾値は意味が変わる)。

### 併記するもの(台日ごと・群ごと)

1. **発生率**(日単位で扱う): 同じ台の同じ日の台日は独立ではない(客の集中、稼働の日変動を共有する)ので、**台日の二項検定は使わない**。
   - **比較する日・台日の選び方を、分析の開始時に固定する**: 対象群(例: イベント日、機種×月)と、比較群(例: 同じ機種・同じ曜日区分の、対象日を除いた他の日)を、結果を見る前に台帳に書く。比較群の基準率は、**対象群と別の標本**(対象日を除く)から作る。同じ標本から期待率を作って、その標本を検定しない。
   - **日を1観測にする**: 日ごとに、層(機種×イベント条件)の「大負け×高回転」の台日数と、稼働台日数を出し、日単位の割合(または超過数)を1観測とする。
   - **検定・区間**: 日ラベルの並べ替え(曜日の中)、または日単位のブロックブートストラップで、対象群と比較群の差の区間を出す(機種数などで BH 補正)。台日数だけが多く日数が少ないものは、日数nを併記して、区間が広いことを示す。
2. **反復**: 台番号(固定された座標)ごとの発生回数と、別の日の再発。複数の台番号にまたがる集中(島・列・並び)は、その単位で別に数える(台番号と位置を二重に数えない)。
3. **RB確率**(利用可能な機種): 台日のRB確率の期待比と事後確率。AT機は、AT初当り率(監査Aの機種のみ)を別に出す。
4. **他の手がかり**: 前後日の同じ台番号の回転数・差枚(履歴軸)、隣の台。

### 区別すべき高稼働(混ぜない)

高回転は、設定以外の理由でも起こる。次を**先に層として分けて**、層の中の過剰を見る。

- **新台**: 導入後7日(N1)。設定と無関係に高回転になる。
- **機種人気**: その機種の通常日の回転数分布(機種内の上位分位)。人気機種は常に回る。
- **イベントの期待感**: イベント日・名指し・取材日と、通常日を分ける。

### 位置づけと限界

- **「大負け×高回転」だけで該当した台は、「要確認候補」**に留める。
  - **③同じ台番号で別の日にも再発**、**④層の比較群に対する日単位の区間が0を外れる**は、現象の反復・偏りを示すだけで、設定の根拠とは限らない。③④があっても、**「反復する要確認候補」**であり、「不発の高設定候補」には昇格しない。
  - **「不発の高設定候補」に昇格できるのは、当たりに関する根拠があるときだけ**: ①RB確率(そのホール・機種で判別に使えると確認済み)の期待比が高い、②AT初当り率(監査でAの機種)が高い(①②は別の指標・別の族)。根拠の列を区別して示す。確認済みのRB列・AT初当り列がない機種は、昇格できない(要確認候補のまま)。
  - **機械割差・差枚は、「大負け」の選抜条件そのものなので、根拠に数えない**。**高回転だけで高設定と確定しない。**
- **高回転は、必ず、同じ回転数の台と比べた当り率(回転数帯を揃えたO/E。RB確率またはAT初当り率)とあわせて見る。** 6000G以上の割合だけで選ぶと、客が長く打つ位置・日(角番の型など)を拾うことがある。回転数と当り率の両方が上がるものが、設定の手がかり(V1の対象外の高稼働の台では、機械割差も併記する)。
- **日次の合計だけでは、負けてから回されたのか、先に好調で後から負けたのかは判別できない。** このスキルは日中の推移データを扱わないので、経過は推測せず、報告に、この限界を書く。
- マスターにAT初当りの確率がない機種は、当り率で確かめられず、回転数だけでは判断を保留する。

## 水準の分析(L1〜L5)— 日を問わず強いもの

**必須。** 曜日・イベントなどによる「他の日との差」とは**別に**、日を問わず強い機種・島・位置・台番号・末尾を見る。

- **単位**: 機種(L1)、島(L2)、位置=角番・列(L3)、台番号(L4)、末尾(L5)。
- **指標**: 差枚、機械割差(pt)、回転数、RB確率(利用可能な機種)。出玉系は、差枚と機械割差を**1つの証拠**として数える。
- **窓**: 直近1・2・3か月(対象日を含めない、基準日までの暦日)。それぞれの窓の値を並べる。
- **比較の相手**: ホール全体、同タイプの機種(ジャグ・ハナハナ・BT・AT)。台番号は固定された座標なので、L3(位置)とL4(台番号)は別の単位として並べるだけで、「台番号の強さと場所の強さの切り分け」は行わない。
- **継続性**: 月ごとに、ホール全体との差の符号と大きさを並べる。3か月の平均だけでは、直近の落ちを拾い損ねる(平均は高いが直近の月は低い、がある)ので、**直近の月の値をあわせて出す**。
- **見かけの強さに注意**: 機種の人気・稼働量が多いだけの機種は、差枚が大きく見える。**機械割差で見て、回転数で層別**(回転数を揃えた比較と、揃えない比較を並べる)。回転数が高いのに当り率・機械割差が低いものは、客の好みの位置で、設定ではない(高回転軸と同じ注意)。
- **選ぶ数の目安**(初期値): 機種3、島2、角番1、台番号10、末尾2。台数が少ない機種・島や、台番号ごとの上位は、運の幅が大きいので載せない。
- **再現確認(候補選定後の月)**: 選ぶのは [t−3か月, t) のデータだけ。**次の1か月で、同じ指標の値(ホール全体との差)を検証**する。選んだ後の月でも、差が残るものを候補とする(翌月検証。新台は除く)。選定月の値だけで報告しない。

**実行・報告との結び付き**:

- 台帳に、L1〜L5を、単位ごと・窓(H4〜H6と同じ暦日の窓)ごとに枝番で立てる。**日内の対比の軸(T、H、P、X)より先に**回す(水準を先に出さないと、日内の対比に混ざる)。
- 日内の対比(T・P・X)は、**水準を引いた残差**でも見て、「その日だけ強い」と「いつも強い」を分ける。
- 統合報告に、「水準」の節を**必ず**設ける。上位の単位ごとに、3つの窓、月別、翌月検証の結果を並べる。翌月検証がまだできない候補(選定後の月が揃っていない)は、**「未検証」と明示**する。
- 水準(L)の結果は、次の S1(ホール全体 / 機種集中)と統合する。

## ホール全体が強い日と、機種集中の日の分離(S1)

**必須。** 「その日、ホール全体の水準が高い」ことと、「一部の機種に好調台が集中した」ことは、別のしくみ(全体への投入 / 特定機種への投入)で、混ぜない。

- **ホール全体の水準**(日ごと): 全台の差枚合計・平均差枚と、機械割差(pt、基準を明記)。回転数もあわせて出す。
- **機種ごとの好調台**: 好調台の定義(例: 台日の機械割差が基準以上、または RB確率・AT初当り率が確認できる機種はその事後確率が基準以上)を、**分析の開始時に台帳に固定**する。機種ごとに、好調台の台数と割合を出す。
- **集中度**: 好調台の機種別の分布の偏り(上位1〜2機種が占める割合、またはハーフィンダール指数)。
- **日の分類**: 全体型(多くの機種で割合が高い)/ 集中型(少数の機種に偏る)/ どちらでもない。
- **見かけの差に注意**: 機種構成や稼働台数が変わると、台数や割合が変わる。次を必ず行う。
  - 好調台の台数は、その日の機種別の稼働台数で割った割合でも出す。
  - 期待値は、その日の機種構成・稼働台数を固定した基準(機種自身の水準、L1)から作る。機種の水準を引いた残差でも分類する。
  - 稼働台数が少ない機種(2〜3台)は、1台で割合が大きく動くので、台数の下限を決める。
- **水準分析・イベント分析との統合**:
  - 水準(L1)の強い機種が、集中型の日の中心機種かを突き合わせる(いつも強い機種が目立つだけではないか)。
  - イベント日・公約の日(T7・T8)を、全体型 / 集中型に分類し、イベントごとの型の内訳を出す。名指し機種を含む / 除く の両方で見る。
  - 報告では、水準の節とイベントの節に、S1の分類を併記する。

## 反証確認(F1)

**候補ごとに必須。** 候補(族のp、セルのq、水準の上位などで拾ったもの)が、**事前に決めた比較条件**でも同程度の結果として出ないかを確認する。

- **比較条件は、分析の開始時(結果を見る前)に、軸の種類ごとの規則として台帳に固定する。** 既定の規則:
  - 日付の下一桁D・DD: 隣接する日付(D±1、DD±1)。D・末尾は0〜9を円環とみなす(7なら6と8)。
  - 曜日: 隣接する曜日。
  - 末尾: 隣接する末尾(±1)。候補が「D=末尾」の対角なら、同じ組み合わせの非対角。
  - 角番: 隣接する角番(角1なら角2)。
  - イベント・公約: 同じ曜日・同じ機種構成の非イベント日。
  - 機種・島: 同タイプの、台数が近い機種・島。
- **結果を見てから、都合のよい比較条件を選ばない。** 規則に載っていない比較を足すときは、足した理由と時点を台帳に書き、**足した比較も、多重検定の対象(族に含めてBH補正)として扱う**。
- 判定: 候補の効果が、比較条件の効果と、有意に違うか(差の検定)を見る。「同程度の結果が隣でも出る」なら、候補固有ではなく、軸全体の水準(または客の集中)の可能性が高いと報告する。
- 例: 「7のつく日×末尾7」なら、6・8のつく日 × 末尾6・8 や、7のつく日 × 非対角の末尾と比べる。
- 結果ファイルの `falsification` に、済 / 未実施 / 該当なしを書く。**反証確認が未実施の候補は、候補として載せるが、その旨を明記する。**

## 新台の導入後7日(N1)

- **導入日**: そのホールのDBでの機種の**初出日**。経過日 d=0〜6(導入後7日)を個別に見る。
- **指標**: 回転数、差枚、機械割差、RB確率(利用可能な機種)を、経過日ごとに出す。
- **比較**: 同ホール・同タイプの既存機種、およびその機種自身の導入後8日以降(8〜35日)。
- 新台は、設定と無関係に高回転になる。**回転数の高さは根拠にせず**、機械割差・RB確率の水準を、自分の導入後8日以降と比べる。
- 他の軸の分析(T・H・P・M・X・L)からは、新台期間を除く(`axis_scan.is_new_machine`)。
- **近似の限界**: DBの最初の日に既にある機種は、導入日が分からないので新台にしない(DB開始直後の導入との区別がつかず、取りこぼしがありうる)。

## 期間の取り方

**直近3か月を主にする。** 全期間(1年以上)でまとめると、ホールが設定の入れ方を変えたときにトレンドが薄れる。報告の表は、**直近3か月、レジーム境界以降、全期間**の順に並べ、結論と行動メモは直近3か月を基準にする。直近3か月は日数が少なく(水準あたり十数日)、検出力が低いので、直近3か月だけで出たものは「候補」とする。全期間と向きが逆のときは、レジームの変化の有無をユーザーに確認する。台帳への登録や、機種別の個別セルを載せるときは、補正(BH)後の扱いを必ず併記する。

**分析期間(報告の表の期間)と、履歴窓(H4〜H6の特徴量の窓)は別のもの。** 混ぜない。

## 統計の手順(共通)

1. **データ準備**: `mr.load_machine_days(db, 開始, 終了)` で台日表。区分(`find_spec` の category)でノーマル・BT / それ以外に分ける。配置は `machine_layout_history` を日付に対応する版で結合する(改装と配置替えで section が変わる)。**G=0の行は捨てずに残す**(回転数の分析では有効な観測。率の指標だけ計算不能として除く)。欠測日も、理由つきで残す(履歴軸)。
2. **期間**: レジーム境界を分け、前後を混ぜない。台番号・台数が変わる機種は、前後を混ぜない。
3. **期待値**: 機種×回転数帯(2000G刻み)の基準を作る。客数の増減を除くため、その日の区分全体の `ΣG÷Σ期待G` を期待Gに掛ける。**履歴軸・翌月検証・開店前に使う評価では、基準を対象日より前だけで作る**(下の「未来データを使わない規則」)。
4. **時間軸のラベル**: 曜日、D、DD、ゾロ目・強ゾロ目、`EVENT_SERIES.jsonl` の系列(ユーザー確認済み)。系列は改装前後に分け、同じ日付の取材などは独立の証拠として数えない。
5. **検定**: 日付ラベルを、曜日の中で入れ替える(曜日の軸だけは月の中)並べ替え検定(2000〜4000回)。位置軸×時間軸は、「時間水準の中と外で、位置の効果が違うか」の差の差。族(時間軸×位置軸×区分×指標)ごとに、**スチューデント化した z の最大**で族のp、セルのpは両側、全セルをBH補正。
6. **名指し機種の除外(イベント・公約の分析)**: その日の公約の名指し(`PAST_PROMISES.jsonl`)を、`MODEL_ALIASES.csv` で正式名にして除く。除かないと、予告された機種が回るのを「効果」と読む。ノーマル・BT側の名指し・客数の除外は未実装。
7. **並び**: 隣接ペアの残差の積は、同機種・同日の平均を引き、3台以上の機種だけにする。引かないと全台系を並びと取り違える。
8. **台別・台日別の確認**: 候補が出たら、日別の推移、同じ機種の他の台、同じ台の他の日、少回転の台日を確認する。
9. **再現確認**: 改装前、月別、前半後半で向きを見る。向きだけでなく大きさも書く。

### 未来データを使わない規則(履歴軸に限らず、全軸に適用)

- **対象日(または評価月)を含めない。** 基準値(機種×回転数帯の基準率)、客数補正、閾値・分位、候補選定のすべてを、**対象日より前**(< t)のデータだけで固定する。「以前(≦t)」と読まない。
- **客数補正は、当日実績を使うかで基準を分ける。** 現行コードの客数補正(`axis_scan.add_expectations` の `traffic` = その日の区分全体の `ΣG÷Σ期待G`)は、**対象日当日の総回転数**を使う。これは、開店前には分からない値なので、基準値を過去だけで作っても、**開店前の評価には使えない**。
  - **`as_of`(開店前に使える評価)**: 客数補正は、**当日実績を使わない方法**を指定する。例: 直近の同じ曜日(過去N週)の客数指数の平均、または補正なし(補正あり・なしを並置)。使った方法を台帳の scope に書く。
  - **`ex_post`(事後分析)**: 基準・分位・選定は対象日より前だけで作るが、客数補正に**当日の総回転数**を使う。「その日の客数の増減を除いたとき、何が強かったか」を見るのには使えるが、**開店前の予測・推奨には使えない**。報告で「事後分析」と明示する。
  - 台帳の `basis`・結果JSONの `basis` は、`as_of` / `ex_post` / `in_sample` のどれか。
- **翌月検証・開店前に使う評価**: 候補は [t−3か月, t) だけで選び、基準も同じ範囲で作る。検証月のデータは、選定にも基準にも使わない。検証月の中の日を評価するときは、その日より前までで基準を更新するか、検証月の前で固定する(どちらかを台帳に書く)。
- **期間全体で基準を作った出力は `basis=in_sample`**(説明用)。現行の `axis_scan`・`unit_time_scan` は、期間全体から基準を作り、客数補正にも当日実績を使う(上の実行手段の現状)ので、`in_sample` で、**そのまま「翌月検証済み」「開店前に使える」と扱わない**。
- **`next_month` を「済」にできる条件**: 選定と基準が検証月より前に固定されている(`basis` が `as_of` または `ex_post`)こと。それ以外は「未検証」。
- **「開店前に使える」と書けるのは `basis=as_of` だけ**。`ex_post` と `in_sample` は、事後分析として扱う。
- 候補の選定に使った期間と、検証に使った期間は、台帳の window に両方書く。

### 推定・解釈の注意(共通)

- **回転数帯で揃えたO/Eは、稼働が日によって大きく違う軸(曜日、イベント日など)で偏る。** 稼働の多い日は、高い回転数帯の基準と比べるため、O/Eが低く出る。**稼働が違う日を比べる軸のRB結果は、帯補正あり・なしを必ず並べ、符号が割れたら判定しない。** 同じ日の中の比較(角番と他の台など)は、この偏りを受けない。
- **回転数は、設定の結果(当たりが多く打たれる)でもあり、客の集中の結果でもある。** 回転数帯で揃えると設定の優位を過小評価しうる。揃えた比較と、揃えない比較(事後確率)を並べる。
- **少回転の高い機械割(数百G)は、設定のしるしではない。** 同じ台の他の日の水準と比べる。
- **AT機の機械割は、1台日のばらつきが大きく、機械割が上がらないことは「設定が入っていない」根拠にならない。** ホールごとに台日の標準偏差を実測して、検出力を書く。評価は、機械割差だけでなく、高回転の台日の割合(V1)と、AT初当りの率(監査でAの機種)に寄せる。
- **事前分布**: 既定の一様な事前のまま、事後確率の絶対値は、確率そのものとして読まず、**同じ条件の群どうしを比べる目安**として使う(設定の実際の配分は分からない。設定が4段階の機種では、事前の設定5以上が50%になる)。報告には「一様な事前の値」と書く。`REALISTIC_PRIOR`(設定1=55%)は、結論が事前に左右されないかを見る感度確認にだけ使う。比較(差)、RB確率、機械割、勝率は事前に依存しない。
- **AT機のRB判別はホール別の監査**(`backtest/at_rb_audit.py`、`document/registry/AT_RB_AUDIT.csv`)。bb/rbに入るものの意味はホールで違うので、全ホールをまとめた平均では判定しない。判定は、そのホール単独の実測が、マスターの設定1〜6の範囲(余裕5%)に入る列が1つだけ、台日300以上、分散比5以下、のときA。`load_specs(hall="<ホール名>")` のように**ホールを渡したときだけ**、Aで、ホール間のばらつき(最大÷最小)が1.3以下の機種に、`at_judgeable` と `at_column` が付く。

## 報告の書き方(統合報告)

統合報告は、**台帳と全結果ファイルから**作る。長い出力の貼り付けにしない。

1. **台帳の状態集計**: 完了・データ不足・失敗・未実施の件数。**未実施・データ不足・失敗は、軸ごとに理由を一覧にする**(必須)。照合の7項目の結果。
2. **必須節**: 水準(L)、ホール全体 / 機種集中(S1。水準とイベントの節に分類を併記)、高回転(V1)、新台(N1)、履歴(H1〜H6)。各節に、検出力、指標ごとの結果(出玉系は1証拠。RB確率とAT初当り率は別)、候補、限界。
2'. **反証確認と翌月検証の状態**: 候補ごとに、反証確認(F1)の結果(済・未実施)と、翌月検証(済・**未検証**)を表に並べる。追加した比較条件があれば、理由と、多重検定に含めたことを書く。
3. **日内の対比の節**(T・P・M・X): 族と、セルの数、p<0.05の数(偶然の期待数と並べる)、BH補正後の数を表で出す。
4. 目立つセルは、日数、台数、区間、機械割差と勝率(事前に依存しない指標)を併記する。「安牌」「法則」と書かない。
5. 期間は、直近3か月、レジーム境界以降、全期間の順。
6. 見つからなかったときも、「検出力が低い」と、見た軸の一覧を書く。
7. 有望な候補は、台帳(`HYPOTHESIS_LEDGER.md`)に、**判定の基準と判定日を先に決めて**事前登録する。結果の要約は instinct に残す(1セッション1〜3件)。
