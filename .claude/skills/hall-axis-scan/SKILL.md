# ホール軸総当たり(hall-axis-scan)

## ユーザーの要望(2026-10-02)

**全軸・全要素を網羅して調べる。指示を待たない。** 軸を1つずつ頼まれて出すのではなく、最初の報告に、下の軸カタログ全体の結果(見た、見ていない、理由)を入れる。
回せなかった軸は「やらなかった」と、理由つきで報告に書く。黙って落とさない(`hall-analysis-checklist` と同じ約束)。

### 既知の穴(必ず報告に書く)

1. **RB判別できるAT機(ホールごとの監査、2026-10-03)**: 監査 `backtest/at_rb_audit.py` と登録簿 `document/registry/AT_RB_AUDIT.csv`(**ホール別**)。**bb/rbに入る意味はホールで違う**(マギアレコードは、楽園のbbが1/350で設定1の1/241より遅く、AT初当りではない。みとやなどは1/230〜1/240で合う)ので、全ホールをまとめた平均では判定しない。判定は、そのホール単独の実測が、マスターの設定1〜6の範囲(余裕5%)に入る列が1つだけ、台日300以上、分散比5以下、のときA。bbかrbが常に0のホールでは、bb+rbは別の列として数えない。`load_specs(hall="楽園蒲田店")` のように**ホールを渡したときだけ**、Aで、ホール間のばらつき(最大÷最小)が1.3以下の機種に、`at_judgeable` と `at_column` が付く(既知のジャグラーは1.05〜1.18。1.3超は、列の意味がホールで違う可能性があり、確認が取れるまで使わない)。楽園で使えるのは、スマスロ北斗の拳(rb)、戦国乙女4(bb)、ダンベル何キロ持てる?(rb)、盾の勇者の成り上がり(bb+rb)、邪神ちゃんドロップキック(rb)の5機種。東京喰種、からくりサーカス、真打吉宗などは、ホール間のばらつきが大きく、保留。マギアレコード、新鬼武者2/3は、楽園では範囲外。`axis_scan` は `hall` を渡して、そのホールの監査を使う。モンキーターンVは、列の意味がユーザー確認待ち(保留)。
2. **事前分布(2026-10-03、ユーザー決定)**: **既定の一様な事前のまま、事後確率の絶対値を「理論値」として使う。** 設定1の実際の配分は分からない(55%は実測で確かめた値ではない)ので、未確認の仮定を足さない。ただし一様も「どの設定も同じ確率」という仮定で、設定4段階(1,2,5,6)の機種では事前の設定5以上が50%になる(アレックス3000G・RB9回で設定5以上が一様0.42、設定1=55%の事前で0.09)。**絶対値は確率そのものとして読まず、同じ条件の群どうしを比べる目安として使う。** 報告には「一様な事前の値」と書く。`REALISTIC_PRIOR`(設定1=55%)は、結論が事前に左右されないかを見る感度確認にだけ使い、既定にしない。将来は、台日の分布から設定の配分を推定する(EM法)案がある。比較(差)とRB確率、機械割、勝率は事前に依存しない。
3. ノーマル・BTのイベント・公約別は、名指し機種の除外と客数の除外を、まだ入れていない(AT等のみ)。
4. 検出力の限界: 1水準が3〜12日だと、数%〜十数%は拾えない。「検出できなかった」と「ない」を混ぜない。

## 指標(機種区分で変える)

- **ノーマル・BT**: RB確率(RB回数÷総回転数)と回転数。比較は、機種×回転数帯(2000G刻み)の基準から出した期待RB回数との比 `O/E`、または台日ごとのRB事後確率。RB列が空の機種(rb=0かつbb>0)は除く。2台機種を落とさないよう、日の条件は「同時稼働台数の最大」に合わせる。
- **それ以外(AT等)**: 機械割(差枚÷3G。基準は同機種・同じ回転数帯の平均)と回転数(同機種・同曜日の平均との比)。**差枚そのものは、回転数が違う台・日を比べるのに使わない**(差枚=3×回転数×(機械割-1))。入替後7日以内の新台は除く。
- **回転数の扱い**: 回転数は、設定の結果(当たりが多く打たれる)でもあり、客の集中の結果でもある。回転数帯で揃えると設定の優位を過小評価しうる。**揃えた比較と揃えない比較(事後確率)を並べる**。
- **少回転の高い機械割(数百G)は設定のしるしではない**。同じ台の他の日の水準と比べる。
- **回転数が多い台日を、「客の集中」と決めつけない**(ユーザー指摘、2026-10-03)。高設定でも、不発で出玉が出ず、粘られて回転数が多くなる台がある。AT機の機械割は、1台日の標準偏差が約21ptで、機械割が上がらないことは、「設定が入っていない」根拠にならない(取材日39台日で、誤差は約±6.6pt、設定4相当の+5ptまで否定できない)。AT初当りの列が取れている機種(ホール別の監査でA)では、**回転数4000〜9000Gの台日を、機械割で3群(不発・中・好調)に分け、AT初当りの率を並べる**(楽園の北斗: 0.84、1.03、1.12)。不発群でAT初当りが多ければ高設定の不発、少なければ低設定寄り。機械割の検定は、台日数が少ないと検出力がないことを、報告に書く。

## 手順

1. **データ準備**: `mr.load_machine_days(db, 開始, 終了)` で台日表。区分(`find_spec` の category)でノーマル・BT / それ以外に分ける。配置は `machine_layout_history` を日付に対応する版で結合する(改装と配置替えで section が変わる)。
2. **期間**: 改装後を主、改装前を再現確認に使う。台番号・台数が変わる機種があるので、改装前後を混ぜない。
3. **期待値**: 機種×回転数帯の基準を、期間全体から作る。客数の増減を除くため、その日の区分全体の `ΣG÷Σ期待G` を期待Gに掛ける。
4. **時間軸のラベル**: 曜日、D、DD、ゾロ目・強ゾロ目、`EVENT_SERIES.jsonl` の系列(ユーザー確認済み)。系列は改装前後に分け、同じ日付の取材(超太陽神・水星神・四星W)は独立の証拠として数えない。
5. **検定**: 日付ラベルを、曜日の中で入れ替える(曜日の軸だけは月の中)並べ替え検定(2000〜4000回)。位置軸×時間軸は、「時間水準の中と外で、位置の効果が違うか」の差の差。族(時間軸×位置軸×区分×指標)ごとに、**スチューデント化した z の最大**で族のp、セルのpは両側、全セルをBH補正。
6. **名指し機種の除外(イベント・公約の分析)**: その日の公約の名指し(`PAST_PROMISES.jsonl`)を、`MODEL_ALIASES.csv` で正式名にして除く。除かないと、予告された機種が回るのを「効果」と読む。
7. **並び**: 隣接ペアの残差の積は、同機種・同日の平均を引き、3台以上の機種だけにする。引かないと全台系を並びと取り違える。
8. **台別・台日別の確認**: 候補が出たら、日別の推移、同じ機種の他の台、同じ台の他の日、少回転の台日を確認する。
9. **再現確認**: 改装前、月別、前半後半で向きを見る。向きだけでなく大きさも書く。

## 報告の書き方

- 族と、セルの数、p<0.05の数(偶然の期待数と並べる)、BH補正後の数を、表で出す。
- 目立つセルは、日数、台数、区間、機械割と勝率(事前に依存しない指標)を併記する。「安牌」「法則」と書かない(勝率30%は負ける。事後の推定は開店前に分からない)。
- 見つからなかったときも、「検出力が低い」と、見た軸の一覧を書く。
- 有望な候補は、台帳(`HYPOTHESIS_LEDGER.md`)に、**判定の基準と判定日を先に決めて**事前登録する。結果の要約は instinct に残す(1セッション1〜3件)。

## 実装の場所

**位置軸×時間軸の総当たりは `backtest/axis_scan.py`(2026-10-03、テストつき)。** 実行:

```
venv\Scripts\python.exe -X utf8 -m backtest.axis_scan --hall 楽園蒲田店 --start 20260707 --end 20260930 --iters 2000
```

RB側はノーマル・BTと、監査でAのAT機(`at_judgeable`、`at_column`の列)、それ以外はOTHER側(機械割と回転数)。族とセルの表(BH補正つき)を返す。
`run_scan(df, ...)` の `F`(族)と `C`(セル)を、報告の表にする。テストは `test/backtest/test_axis_scan.py`。
AT機の列の監査は `backtest/at_rb_audit.py`(登録簿 `document/registry/AT_RB_AUDIT.csv`)。

次の参照実装は、探索時の使い捨てスクリプトで、`axis_scan.py` に取り込めていないものだけが対象:
(TEMPのpickleに依存し、整理前の探索コード)。再利用の前に、必要な部分を `backtest/` に取り込む。

- `dd2.py`: ノーマル・BTのRBの日付軸(D、ゾロ目、強ゾロ目)と、期間のraw作成
