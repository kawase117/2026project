# ホール分析 6パスチェックリスト

## トリガー

- 「◯◯の動向を分析して」「今日は強いですか?」と言われたとき
- ホール分析・機種分析の結果を報告文としてまとめる直前
- `pachinko-live-analysis` スキルの戦略パターンを使って結論を出した後、報告に出す前

## 背景

2026-09-11のセッションで、以下の6項目を**すべてユーザーに指摘されてから**着手した。
初回の報告は毎回浅い。「迎合するな、独立した意見を述べよ」というプロジェクトの最重要ルールは、
分析の切り口を出させている時点で守れていない。指摘を待たず、最初の報告に入れる。

## チェックリスト

報告を書く前に以下を全部通す。**回せなかった項目は「やらなかった」と明示して理由を書く。黙って落とさない。**

### 1. セグメント分割を既定にする

ホール平均・機種平均だけで報告しない。`machine_master.spec_category`
（AT / A+AT / BT / ノーマル / ART）で必ず割る。全体平均では見えない構造が出ることが多い
（実例: 蒲田1の9月、ノーマル +283枚/勝率+9.5pp・BT +171/+9.3pp に対し AT は +4/-0.4pp）。
⚠️ マスターは更新される（`updated_at` を見る）。分析前に区分の値を確認すること。

### 2. 「差があるか」だけでなく「何台あるか」を出す

相対差の検定で終わらせない。**常に高設定があるなら差は要らない**というのがユーザーの立場。
高設定推定台の**絶対数と密度**（1日あたり何台・判定台数の何%）を必ず併記する。
判定は `backtest.bonus_specs` の事後確率で、事前は一様でなく設定1=55%の現実的な分布に置き換える
（一様だと密度が2〜3倍に膨らむ）。

### 3. 推定器が壊れていないかを先に確かめる

代理指標を使う前に、それが設定情報を持つか実データで確認する。既知の壊れ方:

| 指標 | 壊れ方 |
|---|---|
| 勝率（差枚>0） | 設定6のAT機でも4割負ける。分解能が無い |
| 絶対差枚 | 名指し機種はG数が伸びるので効果ゼロでも有意に出る |
| 出率>=1.05 | 4000G以上回った台の40%が該当（生存バイアス） |
| ボーナス確率（AT機） | 機種によっては観測値がベースとほぼ同値なのに出率は跳ねる（相関が弱い） |

**AT機の台単位の高設定判定はできない。** 判定可能機種（ノーマル/BT/A+AT）に限る。
`document/registry/MDE_GATE.md`（`hall-analysis-checklist` とは別スキル配下）で軸・推定器・
暦コストごとの検出力を確認できる場合は先に引く。日付軸(dd_event/strong_zorome/weekday)の
gate列はそのまま使わない（楽観的、詳細はファイル内の警告参照）。

### 4. 交絡を「除外」する前に「狙い目か」を測る

新台・イベント日・高稼働日などを交絡として取り除く前に、**それ自体に張る価値があるか**を
必ず先に測る。安易に「歪み」として除外しようとして訂正された実例がある。

### 5. 予告・結果発表と必ず突き合わせ、当日中に register する

ホール分析と `backtest/announce/` を切り離さない。分析を頼まれた時点で、
- 対象日の予告が登録済みか（`LEDGER.jsonl`）
- **当日の予告が未登録なら、聞かずに下ごしらえまで進めて提案する**
  （`target_date <= db_max` で拒否されるので翌日は不可。下ごしらえは `announce-prep` スキル）
- 結果発表アカウントの投稿が来ていないか（`scraper/twitter_monitor/state.db` の `seen_tweets`）

### 6. 予告本文が押している軸を、そのまま分析軸にする

本文が「ゾロ目日」「末尾0」「ニブイチ」と言っているなら、**その軸で過去を掘る**。
指摘されるまでやらなかった実例では、結果は使える材料だった
（DD11は18日中16日プラス・稼働と曜日を統制しても+46枚 p=0.034・ゾロ目日はノーマル機が勝率+7.1pp）。
